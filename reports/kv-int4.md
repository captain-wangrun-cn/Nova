## 二、方案：为什么 K 和 V 要区别对待

| | 分组方式 | 理由（**文献引用 / 待实测**） |
|---|---|---|
| **K** | 沿 `head_dim` 每 **32 个通道**一组 | K 的离群值是**通道级**的（少数通道长期偏大），小分组让每组有自己的尺子 |
| **V** | 每个 `(token, head)` 的**整条 128 维**一组 | V 的离群值是 **token 级**的，文献上 V 可以更狠 |

两组都用**非对称**量化（`min` / `step` 各存 fp16）：

```
q  = clamp(round((x - min) / step), 0, 15)      step = (max - min) / 15
x' = q * step + min
```

两个 int4 值打进一个 `uint8`（低半字节在前）。存储记账：

| | 每 (head, token) 字节 | × 8 头 × 36 层 | 每 token |
|---|---:|---:|---:|
| K int4 | 64（数据）+ 16（4 组 min/step） | 23040 B | 22.5 KiB |
| V int4 | 64（数据）+ 4（1 组 min/step） | 19584 B | 19.1 KiB |
| **合计** | **148** | **42624 B** | **41.6 KiB** |
| fp16 基线 | 512 | 147456 B | 144 KiB |

`ratio = 512 / 148 = 3.46x`。元数据只占 **13.5%**（20 / 148）—— 不是主要开销。

### 2.1 这个模块**不省显存**，别误会

`F.scaled_dot_product_attention` 必须吃 fp16 的 K/V。所以"先反量化再算注意力"这条路上，
**必须把整段历史反量化成一块 fp16 缓冲，那块缓冲跟原来的 fp16 cache 一样大**。

本模块（`QuantRoundTripCache`）的做法是：**fp16 原值照旧写进 base cache**，只在喂给注意力之前
把 `[0, used)` 拷进工作区并做一次量化→反量化往返。于是：

- **精度**：注意力看到的 K/V 就是 int4 往返后的值 —— 精度损失是**真的**（不是近似）。
- **开销**：每层每步 O(used) 的拷贝 + 反量化 —— 这就是"先还原再算"的真实代价。
- **显存**：工作区**36 层共用一块**（只多 75.5 MiB @ 18432），收益仍只按公式记账。

> ⚠️ 早期版本按**每层各留一块**工作区（36 × 2 × 37.7 MB ≈ 2.7 GB），直接把峰值顶到 **11.8 GiB**，
> Windows 换页后 prefill 从 1.2 s 涨到 19.6 s。改成共用后峰值回到 6.8 GiB。**这类"仪器本身的显存开销"
> 会伪装成"算法慢"，是本次最容易骗到自己的一处。**

## 三、精度：三层证据

### 3.1 量化器本身（合成张量）

`tests/test_kvquant.py`（13 条，CPU 可跑）：

| 测试 | 判据 | 结果 |
|------|------|:---:|
| `test_dequant_matches_formula` | 反量化 == 用**存下来的 fp16 尺子**手算的 `q*step+min` | 逐位一致 |
| `test_roundtrip_error_within_half_step` | 每元素误差 ≤ 本组 `step/2` + fp16 余量 | 通过 |
| `test_group_independent` | 一组量程放大 100x，另一组结果**逐位不变**；不分组时误差爆 10 倍以上 | 通过 |
| `test_constant_tensor_exact` | `max==min` 的退化情形往返无损 | 通过 |
| `test_shapes_and_groups` | group 16/32/128/整条：打包形状、半字节范围、还原形状全对 | 通过 |
| `test_bytes_accounting` | 147456 B / 42624 B / 3.46x | 通过 |
| `test_cache_newest_token_not_stale` · `test_update_multi_token_covers_all_written_positions` | 见**第四节**（两个真实 bug 的回归测试） | 通过 |

> 一个值得记下的细节：**反量化用的是存下来的 fp16 尺子**（`min`/`step` 各 fp16），
> 与 fp32 原尺子算出的值差 ≤ 1% 个 `step` —— 可忽略，但它是"元数据精度"的真实代价，
> 测试里显式钉住了这个上界。

### 3.2 真实 K/V（`probe_kvquant_real.py` [B]，3665 token）

| 层 | K rel_L2 | K 误差/step | K 噪声/激活 | K 通道离群 | V rel_L2 | V 误差/step | V 噪声/激活 | V 通道离群 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 0 | 0.0735 | 0.448 | **0.548** | **65.4** | 0.1617 | 0.497 | 0.153 | 5.0 |
| 6 | 0.1123 | 0.484 | 0.131 | 7.2 | 0.1092 | 0.496 | 0.081 | 1.8 |
| 17 | 0.0938 | 0.484 | 0.123 | 4.3 | 0.1279 | 0.496 | 0.395 | 10.3 |
| 29 | 0.0931 | 0.484 | 0.214 | 4.6 | 0.1040 | 0.496 | 0.089 | 1.8 |
| 35 | 0.1181 | 0.484 | 0.196 | 8.1 | 0.1145 | 0.496 | 0.136 | 2.8 |

- `误差/step` 稳定在 **0.48**（理论中位 0.5）→ **量化器按设计工作**，没有任何系统性偷懒。
- `通道离群` = 最大通道 / 中位通道的激活比。**第 0 层的 K 是 65x** —— 这正是"统一尺子会把小的那批压成 0"
  的那个现象（**文献引用 / 待实测**），而它确实出现了，且集中在**第 0 层**。
- 结果：第 0 层的量化噪声达到该通道激活的 **55%**；K 相对 L2 误差最坏 **11.8%**。

4 条形近干扰事实（格式完全相同，只有地点与号码不同）埋在不同深度，各问一次。
**同一轮内**跑完 fp16 与 int4（`exp_needle.py --kv fp16 int4 ...`），避免跨时间点比较：

| 长度 | 实际 token | fp16 | int4 | 与 fp16 差 |
|---:|---:|:---:|:---:|:---:|
| 2048 | 1894 | 4/4 挑错 0 | **4/4 挑错 0** | +0 |
| 4096 | 3665 | 4/4 挑错 0 | **4/4 挑错 0** | +0 |
| 8192 | 7291 | 4/4 挑错 0 | **4/4 挑错 0** | +0 |
| 14363 | 12728 | 4/4 挑错 0 | **4/4 挑错 0** | +0 |

**逐档零退化，且零挑错** —— 包括**贴着 D33 天花板**的 12728 token。

> ⚠️ **不要把这条读成"int4 无损"。** 4 道题、每档一次，这是个**粗尺子**：它只能证明

> 我们这次是在检索任务上没测出退化，比文献的悲观预期**更好**，但样本量小。

## 四、踩到的坑：0/4 是**接线 bug**，不是精度损失

这一节比结论更有价值 —— 它记录了我们如何避免把 bug 当成"压缩的代价"。

**症状：** `--kv int4` 在 4096 档 needle **0/4**，输出直接是胡言乱语（`'\x00️️'`），
而 fp16 同档 4/4。很容易归因成"int4 精度不行"。

**排查顺序（4 步，每步都能否掉一个假设）：**

1. **先证明量化器没错**（3.1 节）：合成张量上 13 条测试全过 → 量化/反量化/打包/记账都没问题。
2. **短上下文分水岭**：15 token 的 prompt 也崩（`int4k`、`int4v` 单独都崩）→
   **30 token 里不存在"误差累积"，所以这不是精度问题，是 bug**。
3. **接线拆开比**（`probe_kvquant_wiring.py`）：把「模型实际读到的 K/V」和「真正写进 cache 的 K/V」当场比。
   关键对照组是 `copy` 模式（只做拷贝、**完全不做量化**）——它**也崩**，说明问题不在量化里。
4. **`copy` 与 fp16 仍差 70.6**（只差在**最后一个位置**）→ 定位到写入范围算错。

**根因（`QuantRoundTripCache.update`）：**

```python
used = int(self._base.pos.item()) + 1     # ❌ 只对 decode（n=1）成立
```

`StaticKVCache.update` 在**多 token**时会**内部转调 `append_prefill`**，而 `pos` **不推进**
（推进在 `GraphDecoder.prefill` 收尾处）。所以 prefill 时 `pos + 1` = 1，**只有第 0 个位置被拷进工作区，
1..n-1 位置留在工作区的 0 上** —— 注意力看到一片零。改成：

```python
n = key.shape[2]
start = int(self._base.pos.item())
used = start + n                            # ✅ decode 与 prefill 都对
```

**为什么 `residual` 救不了它：** `--kv int4res` 在 15 token 时 `keep = used - 128 = 0`，
**一个位置都不该被量化**，本该与 fp16 完全一致 —— 却也不一致。这个"本该恒等却不等"的反常
是本次的**决定性线索**。经验写下来：

> 设计一个"应当恒等"的对照组（`copy` / `residual` 大于上下文），它的失败比任何指标都更快定位 bug。

**两条回归测试**（都进 `tests/test_kvquant.py`）：
`test_update_multi_token_covers_all_written_positions`（多 token 走 `update`）、
`test_cache_newest_token_not_stale`（decode 的最新位置）。

修完后 `copy` 与 fp16 **逐位一致（0.00000，logits 差 0.0000）**，int4 全部恢复 4/4。

## 五、开销：「先还原再算」到底多贵

`probe_kvquant_real.py [C]` —— **同一轮内交替两遍取小值**（AGENTS.md 第六节第 4 条：跨时间点的数字不能比）：

| 条件 | prefill fp16 → int4 | decode fp16 → int4 |
|---|:---:|:---:|
| n=3665，cache `max_len` **3697**（余量充足） | 1.35 s → 1.41 s = **1.0x** | 66.2 → 129.9 ms/token = **2.0x** |
| n=3665，cache `max_len` **18432**（贴近 8GB 上限） | 1.39 s → 2.07 s = **1.5x** | 140.9 → 706.8 ms/token = **5.0x** |

在 `exp_needle.py` 自己那套环境（`max_len=18432` + 每题 4 个 needle 的连带开销）里更糟：

| 实际 token | prefill fp16 → int4 | 倍数 |
|---:|:---:|---:|
| 1894 | 1.2 s → 10.1 s | 8.4x |
| 3665 | 1.4 s → 25.0 s | 17.9x |
| 7291 | 3.1 s → 80.1 s | 25.8x |
| 12728 | 7.4 s → 179.7 s | 24.3x |

**同一份代码、同一个 n，只把 `max_len` 从 3697 提到 18432，倍数就从 1.0x 涨到 1.5x（prefill）/ 2.0x→5.0x（decode）；
再进 needle 那套环境就变成 26x。** 把它钉死：`exp_needle.py --kv int4 --max-len 4200 --lens 4096` → prefill **1.5 s**（vs 26 s）。

**结论：**

1. **算法上，朴素"先还原再算"每 token 慢 2–5x**（同轮实测）—— 光这一条就不可接受，decode 是我们最在乎的路径。
2. **朴素实现会把显存压力变成时间**：工作区 + 每步几十个临时张量（约 20 个 × 15–30 MB × 72 次/步）
   在 8GB 卡上触发换页/分配器 churn，倍数再翻一个量级。**归因标注：这一条是 `推测`** ——
   证据是"倍数随 `max_len`（而非 `used`）单调涨"+ 峰值 6.87 GiB 贴近 8188 MiB，
   但我没有把"换页"与"分配器碎片"分离开测。（Windows/WDDM 会静默换页到主存，D33 那次 375.9 s 的断崖也是同一现象。）
3. **用户文献那条判断被我们的数据支持**（**文献引用 / 待实测 → 现已部分实测**）：
   prefill 阶段 dequant 是**纯亏**（算力受限，白花）；收益只在 decode 的显存与带宽上，
   而我们在 decode 上实测到的是 **2–5x 的净亏**（因为还没省下任何带宽）。

## 六、为什么"先还原再算"这条路是死的

```
SDPA 要 fp16 K/V  ──►  你必须有整段 fp16 K/V  ──►  显存一点没省（1.41 GiB → 同样 1.41 GiB）
                              │
                              └──► 每步重建它 ──►  O(n) 拷贝 + O(n) 反量化 ──►  decode 2–5x 慢
```

**两条出路（都还没做）：**

| 路线 | 怎么做 | 工程量 | 风险 |
|---|---|---|---|
| **A. 融合 dequant 进 attention kernel** | 写 Triton：SDPA 直接读 int4 + scale，在寄存器里还原 | **大**。要自己实现 online softmax + GQA 展平 + `is_causal` + 加性 mask；本机 has Triton 3.2.0 但不支持 flash attention | 高（对不上参考实现就没有可信度） |
| **B. 分块 dequant + 在线 softmax** | 一次只还原一个 block，边算边累加 | 中。仍需自写 attention | 中 |
| **C. 换推理引擎（vLLM / TRT-LLM 的 FP8/INT8 KV）** | 直接用现成实现 | 小 | **撞 D06**（全在自己栈里），基本排除 |

**判断标准（什么时候值得写 A）：**
先做**第九节的细尺子**。如果 int4 在更长/更密干扰下仍无退化，那 3.46x 的收益才值得那块工程量；
如果一加压就掉，说明这套分组方案本身要改（比如 K 改按 **token 维**分组），**改完再谈融合核**——
否则会把一块要推倒重来的量化方案固化进 Triton 里。

**顺带一个算术结论：int4 单独不够。** 262144 × 41.6 KiB = **10.4 GiB**，
D17 的 7GB 预算内只剩约 3.8 GiB → 还差 **~2.7x**。所以即便融合核写完，
仍需叠跨层 KV 共享（2–4x，**要训练**）或 MLA（~4x+，**要训练**）。

## 七、与 S4 记忆模块的表示空间规矩（进 D34）

S4 的记忆**就是 K/V 张量**（D07 存 safetensors），D09 要求表示空间冻结。
若推理时 KV 压 int4、记忆却拿 fp16 存，两边空间就不一致。**本项目定为：**

1. **记忆一律按 fp16 存**（它是"原话"，L0 层承诺无损）；**int4 只是运行时 cache 的存储格式**。
2. 记忆注入 cache 时，**按注入那一刻的 cache 格式量化** —— 量化发生在"写入 cache"这一步，
   与记忆自己的持久化格式无关。
3. 因此 **D09 的冻结判据不变**：记忆之间比的是 fp16 张量；int4 不参与记忆的一致性判断。
4. 将来若真要"记忆也存 int4"（省磁盘），必须**新开决策**并重测取回率 —— 不能顺手改。

## 九、下一步（排序）

1. **细尺子：干扰项数扫描（4 → 16 → 64 条同形事实）+ 更多档位。** 现在只有 4 道题，
   测不出 10% 量级的退化。**这条必须先做**，否则分不清"压缩没问题"与"尺子太粗"。
2. **试 8 位（FP8/int8）**：只要 1.9x，但误差减半、可能完全无损 —— **性价比可能比 int4 高**，
   而且工程上 `torch` 有现成路径。**先量它，再决定是否为了 int4 写融合核。**
3. **量化分组方向对照实验**：K 现在按 `head_dim` 32 通道分组（每 token 独立尺子）；
   文献做法是**按 token 维**分组（每个通道一条尺子，跨 token 统计）。第 0 层 65x 离群说明
   我们这套在首层很吃亏。**这是最可能"便宜地变好"的一改。**
4. **首层（前 4 层）留 fp16** 的代价/收益实测（3.46x → 约 3.1x，换首层无损）。
5. **融合核（A 路线）**：等 1–3 有结论再决定写不写。写之前先定验收：
   与"先还原再算"的注意力输出**逐位或 ULP 级一致**，否则没有可信度。
6. **跨层 KV 共享**（要训练）—— 与 1–5 并行无依赖，排在里程碑 2。
