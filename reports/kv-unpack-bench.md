# E4 · 解包微基准：int8 融合核可行，**int4 结案**（2026-09-23）

> **一句话结论（已核查）**：同一套访存模式、同一个上限（232.5 GiB/s）下，
> **int8 的反量化能打到 200.5 GiB/s（86.3%）⇒ 融合核有戏**；
> **int4 打包解包只有 53.4 GiB/s（23.0%）⇒ 结案** —— 而且它**比 fp16 还慢**
> （同一份 KV：int4 0.73 ms vs fp16 0.54 ms）。D30 的教训（"访存省了、算术没融合好"）在 int4 上**重演**。

## 一、方法与判据

`src/diagnostics/bench_int8_unpack.py`：三种模式**共用同一个访存模式**（`M=1`，即 decode 一步的读法），
单层 KV（65536 token × 8 头 × 128 维 = 0.125 GiB fp16）：

| 模式 | 读什么 | 每次读 |
|---|---|---|
| `fp16` | fp16 原样（**基线**，用来验证 harness 本身能到顶） | 0.125 GiB |
| `int8` | uint8 + 每 32 元素一组 `min`/`step`（fp16） | 0.070 GiB |
| `int4` | 打包 uint8（2 nibble/字节）+ 每组 `min`/`step` | 0.039 GiB |

每个 program：读 → 解包 → 反量化 → 乘固定查询向量 → `tl.sum` 写一个 partial。

**判据**（与 232.5 GiB/s 纯读上限比）：**≥ 50%** ⇒ 融合核有戏；**< 25%** ⇒ 结案。

## 二、结果（`clocks.sm` 2250–2490）

| 模式 | 每次读 | 耗时 | 有效带宽 | 相对上限 |
|---|---:|---:|---:|---:|
| `fp16` | 0.125 GiB | 0.541 ms | **230.9 GiB/s** | **99.3%** |
| `int8` | 0.070 GiB | 0.351 ms | **200.5 GiB/s** | **86.3%** |
| `int4` | 0.039 GiB | 0.731 ms | **53.4 GiB/s** | **23.0%** |

**同一份 KV 的端到端耗时**：`int8` 是 fp16 的 **0.65x**（快 1.54x）；`int4` 是 **1.35x**（**更慢**）。

### 不是调参问题（block × warps 四组）

| BLOCK / warps | fp16 | int8 | int4 |
|---|---:|---:|---:|
| 2048 / 4 | 98.7% | 85.5% | 23.6% |
| 4096 / 4 | 99.3% | 86.3% | 23.0% |
| 8192 / 4 | 99.2% | 86.0% | **18.0%** |
| 8192 / 8 | 98.8% | 85.7% | **17.9%** |
| 16384 / 8 | 99.1% | 85.7% | **16.3%** |

int8 稳定在 **85.5–86.3%**；int4 随 block 变大反而更差（16–24%），
说明瓶颈在 **ALU（位操作 + nibble 重排）**，不在访存。

## 三、结论

1. **int8 融合核：可行，值得写。** 86% 的带宽利用率意味着"KV 字节数减半"能**真兑现成速度**
   （0.65x 耗时）。这是 D38 选型的直接支撑。
2. **int4 打包：结案。** 23% < 25% 的门槛，且**比 fp16 更慢** —— 省下的带宽被解包算术吃光还倒亏。
   ⇒ 除非改用硬件 nibble 指令或换 CUDA/CUTLASS 重写，**int4 只作为存储格式保留**，不作为性能路径。
3. **这条把 D34 的"先别写融合核"推进了一步**：现在可以写核了，但**靶子是 int8，不是 int4**。
4. **待实测**：完整 attention 核（online softmax + GQA 广播 + causal）的实际收益 ——
   本实验只证明**访存+反量化这一段**不拖后腿，不证明整核能到 86%。
