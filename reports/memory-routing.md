# E1 · 记忆路由：段级代表 K 该选谁？（2026-09-22 · **判据未达，不 adopt**）

> **一句话结论（已核查）**：**段级静态代表 K 路由达不到判据** —— 三个段长档上 `recall@4` 最高 0.75
> （要求 ≥ 0.95）。而**侧会话"用范数最大的、不要用平均"这条判断被证伪**：
> `top-‖K‖` 在每一档都明显差于 `mean-K`（最差一档名次跌到 93/112）。
> 精确路径（现有 `MemoryStore.scores()`）`recall@4` **恒为 1.00**，但 3.2 s/题。
> **旋转不是变量**：pre-RoPE / 注入帧旋转 / 旋转后平均，三者在各档几乎完全一致。

## 一、测的是什么

侧会话的两级索引构想：**每 256 token 一段、每段留几条代表 K**，于是索引常驻显存、
命中后再拉那一段（100K token 记忆：精确路径要扫 **7.2 GB**，显存放不下；索引只有 27–110 MB）。

代表 K 的选法有两条互相竞争的说法，本实验把**三件事**分开量：

| 方法 | 说明 |
|---|---|
| `mean(pre-RoPE)` | 段内 K 平均，用 pre-RoPE 的 Q 打分（**一次旋转都不需要**，最省） |
| `rot(mean-K)` | 段内 K 平均后整体按注入帧旋转，用旋转后的 Q 打分 |
| `mean(rot K)` | 段内每个 K 先按自己的位置旋转再平均（文献担心的"旋转互相抵消"就是这条） |
| `top4-‖K‖ max / mean` | 段内取 `‖k‖` 最大的 4 条（`‖k‖` 与旋转无关），pre-RoPE 打分 |
| `精确（现有路径）` | `MemoryStore.scores()` —— 上限与**代价基准** |

**真值 = 装着那条事实（号码）的那一段**，不是"精确打分的 argmax"：
实测后者会恒选第 0 段（`scores()` 的公共分量把整段 softmax 质量拉到序列开头），
那衡量的是常分量而不是检索。

## 三、三条已核查的结论

1. **判据未达 ⇒ 不 adopt。** 三个档上路由器的 `recall@4` 是 0.25 / 0.75 / 0.75，**没有一档到 0.95**；
   精确路径三档**都是 1.00**。⇒ 段级静态索引这一层，**现在这几种代表 K 的选法都不够用**。
2. **`top-‖K‖` 明显差于 `mean-K`（侧会话的判断被证伪）。** 判据里那条"`‖k‖` 大的 token 天然占优势"
   在我们的模型上**不成立**：`‖k‖` 与"和当前查询相关"无关。极端例子是 seg=64 的第三题，
   `top4-max` 把真值段排到 **93/112**，而 `mean-K` 排 11。
   - 顺带核查：段级平均 `‖K‖` 的**中位 30.99、最大/中位 1.00x、最小/中位 0.96x**
     ⇒ **没有"attention sink 段"这种量级离群**，"取范数最大"连"挑出异常段"都做不到。
3. **旋转不是变量。** `mean(pre)` / `rot(mean)` / `mean(rot K)` 在每档都几乎完全相同（差距 ≤ 1 名）。
   ⇒ "记忆存的是 RoPE 之前的 K，所以天生适合当路由键"这个**理由**既不成立也不有害；
   真正的瓶颈在**聚合方式**（下节）。

## 四、为什么不行（**推测**，标清楚）

注意力质量是 `softmax` 归一化后的**质量**：段里只要有一个 token 与查询极对齐，它就能拿下这一段的分数。
而路由器用的是 `q·mean(k)` = "段内平均对齐度" —— **一个关键 token 会被 255 个无关 token 稀释**。

`top-‖K‖` 想修这个，但修错了方向：它按**与查询无关**的范数挑代表，
挑出来的多半是"信息量大但与本次查询无关"的 token。

⇒ 要把这条路走通，需要的不是"更好的静态代表 K"，而是**查询相关的粗筛**（先用便宜手段筛出候选段，
再用精确打分在小集合内重排）**或**"把 K 压小但别丢 token"（量化 H 路径，见 E3）。
**两条都还没测。**

## 五、代价（已核查）

| 项 | 数值 |
|---|---|
| 精确路径（现有） | **3192–3278 ms/题**（7168 token 记忆；只扫 K） |
| 六个路由器一起扫（28 段） | **2.03 ms/题** |
| 六个路由器一起扫（112 段） | **4.20 ms/题** |
| 索引体积 @100K token（390 段） | `mean` **27 MiB** / `top4` **110 MiB** ✅ 满足 ≤150 MiB |
| 建索引（含 4 种旋转，28 段） | 185 ms（一次性） |

- **扫一遍 ≤ 1 ms 的门没达**（2.03 ms/28 段），且它随段数线性增长（390 段约 23–28 ms）。
  这 2 ms 里绝大部分是**算子派发 + 两次 `torch.cuda.synchronize()`**，不是算术（einsum 只有几 MB）；
  真要进生产得capture成图或换融合写法。**待实测。**
- 精确路径的 3.2 s/题**还没算**"100K 记忆要扫 7.2 GB"的账 —— 那时显存放不下，
  要么分块搬（PCIe 12.2 GiB/s → 0.6 s/题，见 E6），要么换索引。
