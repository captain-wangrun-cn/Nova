# E2 · 滑动窗口：质量拐点（2026-09-23 · **判据未过，不 adopt；而且代价方向是反的**）

> **一句话结论（已核查）**：局部层做滑窗、每 4 层留 1 个全局层，在 **7291 / 14508 token** 上
> 全部 **0/4**（全量基线 4/4），32K 档 **0/4**。**"窗口盖得住整段"时是 4/4** ⇒ 实现没问题，
> 是"局部层看不到全部上下文"这件事本身在毁检索。而且它**不是单纯的截断**：
> W=4096 在 7291 上下文里，落在窗口内的两条事实也没答出。
> 把全局层比例提到每 2 层 1 个只是把"答不出"变成"**答错**"（1/4 正确、**3/4 挑错**）。
> 代价侧同样为负：KV 省 40–67%，但 **prefill 反而更慢**（窗口掩码打掉了因果稀疏性）。

## 一、实现（已核查）

| 件 | 内容 |
|---|---|
| `WindowedKVCache` | **逐槽位容量**：局部层 `2W` 个槽的 ring，全局层按 `max_len` 全长。与 `StaticKVCache` 同签名 |
| `NovaConfig` | `swa_window`（0 = 关闭）、`swa_global_every`（每 N 层 1 个全局层）、`swa_chunk`（prefill 分块，≤ W） |
| `LeanAttention.window` | > 0 时本层改吃 `window_mask`（宽度 = 本层槽位数），不吃全局掩码 |
| `GraphDecoder` | prefill **分块**（chunk ≤ W，"上一块尾巴 + 本块" ≤ 2W）；局部层掩码按**绝对位置**算 |

ring 槽位 `i` 的绝对位置 `p_i = end - ((end - i) % cap)`（`end` = 最后一个写入位置）；
有效 = **写过**（`p_i ≥ first`）∧ `p_i ≤ q` ∧ `q - p_i < W`。存储序不用重排（注意力对 key 集合求和）。

**验收测试**（`tests/test_swa.py`，6 条全绿）：
① ring 写完 3 圈后每个槽的**内容与它声称的位置一致**；
② **窗口盖得住全上下文时与全注意力逐 token 相同**；
③ 换 prefill 分块大小结果不变；④ 分两次 prefill（第二次 `offset≠0`）与一次 prefill 等价；
⑤ `swa_window=0` 时行为与原来一致；⑥ 掩码恰好选中最后 W 个位置。

### 踩到的真 bug（值得单独记）

`prefill` 把 ring 的 `first` **覆盖**成 `offset`。而 S4 记忆注入的流程是
"先写前缀 `[0,m)` → 再从 `offset=m` 继续 prefill" ⇒ 第二次 prefill 之后，
局部层把 `[0, m)` 全判成"没写过" ⇒ 窗口里只剩当前这一小段 ⇒ **所有问题都答不出（0/4）**。
改成 `min(first, offset)`。**只生成 6 个 token 的测试抓不到它** —— 回归测试
（`test_second_prefill_keeps_window`）是照着这条路径写的。

## 三、滑窗下的 S4 记忆取回（`probe_swa_memory.py`）

设置：6 条事实写进记忆（70 token）→ 从可见历史里去掉 → **120 轮无关对话（3710 token）** →
8 个问题自动检索 + 注入（注入位置在最前面 `[0,70)`）。

| 配置 | 答对 |
|---|---|
| 全量基线 | **7/8**（"咖啡"那条本来就答不出，是本 harness 的基线） |
| W=2048 / 每 4 层 | **5/8**（失败的 3 条都是**串到别的记忆上**："问咖啡答裙子""问出差答不擅长""问乐器答星际穿越"） |

⇒ 注入的记忆一旦掉出局部层的窗口，**只剩 9 个全局层看得见**，取回率掉 2 条。

## 四、结论（已核查）

1. **门控未过 ⇒ 不 adopt**：16K 档要求 4/4，实测 0/4。
2. **失败机制不是"截断"这三个字能解释的**：窗口盖得住整段就 4/4；而 W=4096 在 7291 上下文里，
   落在窗口内的两条事实**也没答出** ⇒ 检索需要**足够多的层同时看到关键 token**，
   只看 9/36 层不够。
3. **提高全局层比例会把"答不出"变成"答错"**：每 2 层 1 全局 + W=4096 → 1/4 正确、**3/4 挑错**。
   在信息过载场景下，半吊子的窗口制造的是**自信的错误**，比"想不起来"更糟。
4. **代价方向是反的**：KV 省 40–67%（且只在 W ≪ n 时），但 **prefill 更慢**
   （窗口掩码打掉因果稀疏性，SDPA 的 mem-efficient 内核**不跳块**）：
   7291 档 5.6 s vs 全量 4.1 s；28977 档 **180.3 s**（同长度因果 prefill 按 O(n²) 外推约 35 s，**慢约 5x**）。
   峰值也没降（7.63 GiB @32K）。
5. **天花板重估**：吃显存的是**全局层**（100K 时 9 个全局层 = 3.5 GiB），
   而"每 4 层 1 全局"正是质量崩掉的配比 ⇒ **滑窗在"保检索"和"省显存"之间没有交叠区**（本轮范围内）。

## 五、这对 260K 意味着什么

- **"少看 token"这条路（滑窗 / 丢 token）在本模型上被证伪**，至少在"不训练"的前提下。
- 于是重心回到 **"不看少，但看便宜"**：**E3（8 位 KV，K 不丢 token）** + **E4（融合核）**，
  以及里程碑 2 的训练侧压缩（gist / 跨层共享 / MLA）。
- 另有一条**实现侧**的独立收获：**带状注意力不能靠"加性掩码"实现**（会把 O(n²/2) 的因果
  稀疏性变成 O(n·2W) 的稠密读）。真要做窗口，得让内核**跳过窗口外的块**（Triton/CUTLASS 的活）。

## 六、结论状态

| 结论 | 状态 |
|---|---|
| ring / 分块 / 逐层掩码的实现正确（窗口盖得住时与全注意力逐 token 一致） | ✅ 已核查（测试 + 对照） |
| 每 4 层 1 全局 + W∈{1024,2048,4096} 在 7.3K/14.5K 上 0/4 | ✅ 已核查 |
| 每 2 层 1 全局时"答不出"变"答错"（3/4 挑错） | ✅ 已核查 |
| 滑窗下记忆取回 7/8 → 5/8 | ✅ 已核查 |
| 加性窗口掩码让 prefill 变慢（28977 档 180 s） | ✅ 已核查 |
| "检索需要足够多的层看到关键 token"是失败机制 | 🧪 **推测**（没做"只把关键 token 留给前 2 层"这类定位实验） |
| 64K 档 | 🧪 未测（全量基线跑不了；滑窗在 29K 已 0/4，判定不必再跑） |

## 七、复现命令

```powershell
$env:HF_HOME=(Resolve-Path .).Path+'\.hf-cache'; $env:TMP=(Resolve-Path .).Path+'\.tmp'; $env:TEMP=$env:TMP
$env:HF_HUB_OFFLINE='1'; $env:TRITON_CACHE_DIR=$env:TMP+'\triton-cache'

& .\.venv\Scripts\python.exe -m pytest tests\test_swa.py -q            # 6 条实现验收
& .\.venv\Scripts\python.exe -u src\diagnostics\exp_swa.py --lens 8192  --max-len 18432 --swa 0 2048 4096 8192
& .\.venv\Scripts\python.exe -u src\diagnostics\exp_swa.py --lens 8192  --max-len 18432 --global-every 2 --swa 2048 4096
& .\.venv\Scripts\python.exe -u src\diagnostics\exp_swa.py --lens 16384 --max-len 18432 --swa 0 1024 2048 4096
& .\.venv\Scripts\python.exe -u src\diagnostics\exp_swa.py --lens 32768 --global-every 2 --swa 4096
& .\.venv\Scripts\python.exe -u src\diagnostics\probe_swa_memory.py --swa 0 2048 --turns 120
```

> ⚠️ 速度类数字都带 `clocks.sm`；跨时间点不可比。加载基座要 ~9 GB 提交量，
> 内存紧张时会报 `os error 1455（页面文件太小）`—— 跑之前先确认提交量有 12 GB 余量。
