# 04 · 异步工具调用

> 目标：**文本流永不中断，工具在后台并行执行。** 像人一边打电话一边翻抽屉找东西。

---

## 一、需求原话

> "我想要的是，能输出文本的同时，做到异步调用 tool，手和大脑同时工作。这个方向可能对机器人会很好，能兼顾对话和操作。"

## 二、对比现有 LLM

```
现有 LLM（顺序模式）:
  "让我查一下..." -> [暂停生成] -> 调用工具 -> 等待结果 -> 恢复生成 -> "明天有雨"

  x 文字生成被 tool 打断
  x 用户看到卡顿
  x 不像人
```

```
本架构（并行模式）:
  Chat 通路:  "让我看看|今天的情况|..."        <- 持续生成，不停
                    |
  Agent 通路: [解析意图] -> [调用工具] -> [等待结果] -> [写入共享记忆]
                    |                          |
                    v                          v
              共享记忆层 <-------------- 结果注入
                    |
  Chat 通路:  "...根据查询|明天有小雨|建议带伞"  <- 收到结果，自然融入
```

## 三、机制：工具头（Tool Head）

**关键：tool call 不是文本 token，是 Agent 通路在隐藏状态层面发出的信号。**

Agent 通路有自己的输出头：

| 输出头 | 通路 | 作用 |
|--------|------|------|
| 文本头 | Chat 通路 | 正常的 next-token prediction |
| **工具头** | Agent 通路 | 输出结构化 tool call（函数名 + 参数），**不走 tokenizer** |

### 单次前向传播中的流程

1. Chat 通路：正常生成下一个文本 token（几十毫秒）
2. Agent 通路：同时分析当前隐藏状态 -> 判断"需不需要调工具？"
   - 不需要 -> 输出 null，零开销
   - 需要 -> 输出 tool call 信号，立即返回
3. 工具在外部执行（真正的异步——不阻塞模型下一步）
4. 结果写到共享记忆的特定位置
5. Chat 通路下一次前向传播时，交叉注意力自动读到新信息

### 预测编码在此的作用

Agent 通路不是每次前向传播都检测 tool call。它用轻量级预测器估算："Chat 通路接下来的生成需不需要工具辅助？"

- 预测"不需要" -> Agent 通路低功耗待机（跳过工具头计算）
- 预测"可能需要" -> 激活工具头做精细判断

**结果：纯聊天时几乎零 Agent 开销，需要时瞬间激活。**

## 四、人脑类比

- 你可以在打电话的同时用另一只手翻抽屉
- 这两个动作由不同脑区控制，通过前额叶共享状态协调，**互不阻塞**
- 对应脑区：Broca 区（说话）+ 运动皮层（动作）+ 前额叶（协调）

## 五、CPU / GPU 分工（天然红利）

**注意：传统的"层卸载"到 CPU 是负优化（CPU 太慢）。真正有价值的分工是做 GPU 做不了的事。**

```
GPU（串行生成，不能停）        CPU（并行，不影响生成）
---------------------------    ---------------------------
生成文本 token                ├─ 执行 tool（查天气、算数）
    |                        ├─ 从 SSD 预取记忆文件
  持续输出                    ├─ KV Cache 换入换出
                             └─ 记忆模块的压缩 / 整理
```

**异步工具架构天生就是 CPU/GPU 分工。这不是优化，是架构红利。**

## 六、机器人 / 具身智能应用

| 机器人需求 | 双通路对应 |
|-----------|-----------|
| 说话（语音生成） | Chat 通路 |
| 操作手臂 / 移动 | Agent 通路 |
| 理解环境（视觉 / 触觉） | 共享记忆层的多模态输入 |
| 边说话边做事 | 两通路并行，互不阻塞 |
| "我去帮你拿"同时伸手 | Chat 生成语言 + Agent 生成运动指令 |
| 拿到东西后说"给你" | 工具结果（触觉反馈）-> 共享记忆 -> Chat 通路读到 -> 生成语音 |

**对比现有方案：** Figure Helix、RT-2 等用一个大模型**顺序处理**（先理解 -> 再规划 -> 再执行）。本架构是**两条流同时工作**，这在机器人领域也是前沿方向。

## 七、实现要点

1. 工具头输出结构化信号，不经过 tokenizer
2. 工具执行结果需写入共享记忆的**特定位置**，供交叉注意力读取
3. 预测器需训练，否则每次都要跑工具头（浪费算力）
4. 需要定义"工具结果注入"的时序——结果到达时，Chat 通路可能已经生成了若干 token，需要优雅衔接

## 八、待确认问题

- 工具结果延迟很长时（比如几秒），Chat 通路如何处理"等待"？（继续闲聊？还是保持沉默？）
- 多个工具并行时，结果如何排序 / 合并？
- 工具失败时如何自然地在对话中体现？
