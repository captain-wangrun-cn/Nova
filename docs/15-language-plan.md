# 15 · 语言策略与训练顺序

> **核心决定：英语是"母语"，中文是后来学的"第二语言"。训练顺序 = 先纯英文 → 后中文 LoRA。**
> 这不是"顺手先用英文跑一遍"，而是架构级约束（见 [13-decisions.md](13-decisions.md) 的 D02 / D03 / D18）。

---

## 一、一句话结论

| 阶段 | 训练什么 | 用什么语言的数据 | 产出 |
|:---:|------|------|------|
| 阶段 0 | 双通路对齐（交叉注意力 + 预测门控） | **纯英文** | 证明架构能工作 |
| 阶段 1 | RP / 对话地基 LoRA | **纯英文** | "怎么做对话、怎么守角色、怎么记状态" |
| 阶段 2 | 中文 LoRA（叠加在阶段 1 之上） | 中文 + 中英混杂 | 中文对话表现 |
| 阶段 3 | 其他语言 LoRA（按需） | 各语言 | 可选扩展 |

**一句话记法：**
> 英文阶段教"怎么做好对话"；中文阶段只教"用中文怎么把这套做出来"。

---

## 二、为什么必须分两步，且英文在前

### 1. 模式只需要教一遍（省数据）

"状态跟踪""角色一致性""语气控制""不抢话"这些是**行为模式**，与语言无关。
英文阶段把模式学进 LoRA 之后，中文 LoRA 只需要学"换一种语言表达同一套模式"。

**预估：中文 LoRA 的数据量只需英文阶段的 30-50%。** 这正是用户"少数据、好效果"理念最直接的落地方式。

### 2. 不要让 LoRA 的容量被"学语言"吃掉

若一开始就中英混合训练，有限的 LoRA 容量要同时承担两件事：

```
有限的 LoRA 容量
   ├── "中文该怎么说"      <- 基座其实已经会（Qwen3-VL 预训练含大量中文）
   └── "对话该怎么进行"    <- 真正需要学的
                              ^ 被前者挤占 -> 两边都不够好
```

分两步后，中文 LoRA 可以专心学后者。

### 3. 数据生态差距

英文 RP / 对话数据集在**数量、长度、质量、标注规范**上都明显好于中文（见 [08-data.md](08-data.md) 第四节的清单）。第一版要验证的是架构，不是中文数据工程，先用好拿的数据。

### 4. 可升级性

每种语言一个独立适配器（D03）：

| 场景 | 结果 |
|------|------|
| 中文表现不满意 | 只重训中文 LoRA，英文能力毫发无伤 |
| 英文阶段改进 | 中文 LoRA 在更好的地基上重训一次即可 |
| 想加日语 | 新增一个适配器，不动已有任何东西 |

### 5. ⚠️ 关于 Token 效率：需要修正的说法

早前文档写过"中文比英文费 2-3 倍 token"。**这个说法对 Llama 系 tokenizer 成立，对 Qwen3-VL 不成立。**

Qwen 的 tokenizer 对中文做过专门优化。**2026-09-21 已实测**（`src/tokenizer_probe.py` → [reports/tokenizer-report.md](../reports/tokenizer-report.md)）：5 组同义中英对照样本（系统提示 / RP 叙事 / 日常对话 / 状态记忆 / 工具指令），用 Qwen3-VL-4B-Instruct 原生 tokenizer 编码。

| 指标 | 实测值 |
|------|:---:|
| 同一批内容 **中/英总 token 比** | **1.02x**（英 183 / 中 187） |
| 中文 | **0.796 tok/汉字** |
| 英文 | 0.213 tok/字符、1.33 tok/词 |
| 中/英 **每字符**成本比 | 3.32x |

**怎么读这组数字：** 总 token 基本持平（1.02x），即 **说中文并不比说英文费 token**。每字符贵 3.32 倍**不是浪费**——同一段内容中文只写 264 个字符，英文要写 858 个字符，中文字符信息密度更高；两者是同一件事的两面，**不能拿每字符数当成本论据**。

- **状态：** ✅ **已实测**（2026-09-21），替代原"待实测"标注
- **结论 1：** "中文 2-3x token" 这条论据在 Qwen3-VL 上**作废**（见 [13-decisions.md](13-decisions.md) **D25**）。
- **结论 2：** "英文省 token / 省显存" 这条理由**不再成立**。英文优先的理由只剩第二节的 1、2、3、4 条（模式只教一遍 + 省 LoRA 容量 + 数据生态 + 可升级性）——仍然足够支撑结论。
- **结论 3：** 中文 LoRA（阶段 B2）**不会因为"中文费 token"而更贵**——上下文长度 / 显存 / 速度按与英文同一套预算估即可。
- **样本边界（待实测）：** 5 组样本、合计 370 tokens，足以否定"2-3 倍"这种量级差异，**不足以断言精确的 1.02x**。S5 建真实语料时重算。
- **注意：** 这不改变 D02 的结论，只改变它的论据强度。

### 6. 补充：原始提案的完整含义（"只预留一种语言"）

用户最初的原话包含**三层**意思：

> "人在长大的时候，是先学习母语，然后在某个时间将另一门语言作为外语，我们可不可以这样，**只预留一种语言**，另一种语言需要之后训练，或者是**推出其他版本**？"

| # | 原始含义 | 本设计如何落地 | 状态 |
|:-:|------|------|:---:|
| ① | **只预留一种语言** | —— | ⚠️ **原始版本做不到，只能降级为"行为层预留"（见下）** |
| ② | 另一种语言之后训练 | 中文 LoRA 在英文阶段完成之后训练（D18） | ✅ 已落实 |
| ③ | 推出其他版本 | 每种语言一个独立适配器，可独立打包分发（D03） | ✅ 已落实 |

**第①层为什么做不到（技术诚实）：**

Qwen3-VL-4B 是**已预训练**的模型，中文能力已经烧进了 tokenizer、embedding 和每一层 FFN 权重里。我们无法"只预留英语"——中文已经在那里，也删不掉（改 tokenizer 会连带破坏已有权重的语义）。

真正意义上"只预留一种语言"只有两条路，**都不在本项目范围**：

| 路径 | 为什么不选 |
|------|------|
| 从零预训练一个纯英文小模型 | 知识从 0 开始，质量远远达不到需求；算力也不够 |
| 对现有基座做语言剥离（unlearning / 语言特定剪枝） | 前沿研究，难度与风险极高，会同时破坏其他能力 |

**本项目实际采用的是"行为层预留"（唯一可做的近似）：**

| 层面 | 做法 |
|------|------|
| 数据 | 英文阶段只用纯英文数据（地基干净，见风险 L4） |
| 行为 | 对话 / RP / 状态跟踪等模式**只用英语教一遍** |
| 内部 | 建议让推理与"内心独白"也走英文，保持母语一致性（**待验证**） |
| 输出 | 中文只作为**表层表达**，由适配器负责 |
| 版本 | 不同语言 = 不同适配器包 = 不同"版本" |

**一句话：** 做不到"只预留一种语言"，但可以做到 **"行为只教一遍，语言只是外壳"**——这是原提案在本项目里能落地的最强形式。

## 三、阶段 0 / 1：英文阶段要打好的地基

英文阶段不只是"学会说英语"，它要一次性建立下面这些能力，**后续所有语言都复用它们**：

| 能力 | 说明 | 验证方式 |
|------|------|------|
| 角色一致性 | 不跳出角色、不 OOC、不忘设定 | 20 轮后仍在角色内 |
| 状态跟踪 | 服装、位置、物品、关系变化被记住并自然引用 | "换衣服"案例测试（见 03） |
| 长上下文注意力 | 前文重要因素不遗漏 | 长对话抽查 |
| 双通路分工 | 对话通路说话、行动通路待机 / 干活 | 闲聊时行动通路开销接近 0 |
| 异步工具头 | 工具信号不走 tokenizer、不打断文本流 | 说话的同时触发工具 |
| 记忆读写 | 记忆令牌正常写入 / 检索 / 巩固 | 跨会话记忆保持 |

**注意：这些是"行为"，不是"知识"。** 4B 的知识量不会因为训练而变多（见 [07-capability-bounds.md](07-capability-bounds.md)），这里练的是**怎么用已有的知识**。

## 四、阶段 2：中文 LoRA 的具体要求

| 要求 | 说明 |
|------|------|
| **必须含中英混杂样本** | 真实 RP 里人名 / 地名 / 专有名词常保持英文。纯中文样本会让模型面对混杂输入时表现异常 |
| 术语一致性 | 人名、地名、技能名保留原文还是音译，全数据集必须统一 |
| 不要重训语言能力 | 基座已会中文；数据应聚焦"对话行为"，而非"认字" |
| 数据量 | 先按英文阶段的 30-50% 起步，做消融（这个比例本身要实验确定） |
| 评测集 | 必须有固定的中文评测集（角色一致性 / 状态跟踪 / 风格），否则无法判断是否退化 |

**中英混杂的处理是中文阶段的核心难点**，也是第一版最可能出问题的地方。见第七节。

---

## 五、阶段 3：其他语言（可选）

按用户原意（D03）：其他语言**保持基座的自然行为即可**，就像"不会英语的中国人"面对英语一样——能认字母、能猜、但不精通。只有当某语言确实有需求时才做适配器。

优先级排序（若要扩展）：日语 > 其他东亚语言 > 其他。

## 六、部署时的适配器切换

| 问题 | 方案 | 备注 |
|------|------|------|
| 语言判定 | 由输入文本判定，或用户手动指定 | 手动更可靠 |
| 单适配器常驻 | 最省显存 | 切换需重新加载 |
| 中英同时加载 | 显存开销 = 两个 LoRA 之和 | 4B 的 LoRA（rank 16-32）约各 50-150MB，可接受 |
| 中英混杂输入 | 需要明确的策略（见下） | **未解决** |
| 量化兼容 | GGUF 对 LoRA 支持有限 | 部署格式本身仍是未决问题（见 06） |

## 七、风险

| # | 风险 | 说明 | 缓解 |
|:-:|------|------|------|
| L1 | 中文能力退化 | LoRA 覆盖基座原有中文能力 | 用固定中文评测集持续监测 |
| L2 | 适配器冲突 | 中英两个 LoRA 同时激活时互相干扰 | 语言判定后**只激活一个**；混杂场景专项测试 |
| L3 | 中英混杂边界 | 一句话里中英交替时行为不可预测 | 中文数据强制包含混杂样本；建立专项评测 |
| L4 | 地基污染 | 英文阶段数据里混入中文，导致地基不纯 | 英文阶段做严格的语言过滤 |
| L5 | 顺序被打破 | 为了"快点看到中文效果"而中英一起训 | 文档即约束：改动必须记录为新的决策 |
| L6 | 数据量比例拍脑袋 | 30-50% 是估计值 | 做消融实验，记录结果 |

## 八、未解决问题

1. 中文 LoRA 的最佳数据量比例（英文阶段的百分之多少）—— 需要实验
2. 中英混杂输入时，应该激活哪个适配器？还是两个都激活？
3. GGUF 量化后 LoRA 是否还能正常工作？若不能，中文方案需要改变
4. 中文阶段会不会顺带削弱英文 RP 表现？（需要跨语言回归测试）
5. 用户最终主要使用语言是中文——如果中文是主战场，"英文当母语"的价值主要落在**训练效率**上，而不是使用体验上。这一点需要在里程碑 2 结束时重新评估。
6. 第 2.6 节的"行为层预留"是否真的成立？即：英文阶段学到的对话 / RP 模式，能否**无损迁移**到中文适配器上？如果迁移率很低，"先英文"的主要收益就消失了
7. 如果英文优先，**基座是否需要重选**？见 [13-decisions.md](13-decisions.md) D19（待定）
