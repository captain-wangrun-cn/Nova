## D01 · 基座选择 Qwen3-4B ⚠️ 已被 D16 取代

- **日期：** 2026-09-21
- **决策：** 使用 Qwen3-4B 作为基座，而非用户最初看中的 NeoHorse-1-9B
- **理由：**
  1. NeoHorse-1-9B 是纯文本（Vision weights are not included），且 9B 双通路 = 18B，4060 装不下
  2. Qwen3-4B 双通路约 7.9B，Q4 约 4.7GB，4060 舒适
  3. 中文 RP 生态成熟，社区量化多
- **状态：** 已定
- **影响：** 决定了全部参数量、显存、速度预算

> ⚠️ **后续变更：** 本决策在 D14（保留多模态）确认后**已被 [D16](#d16--多模态基座qwen3-vl-4b-instruct) 取代**。基座最终为 **Qwen3-VL-4B-Instruct**。此处保留原始记录以备追溯。

## D02 · 英语作为"母语"

- **日期：** 2026-09-21
- **决策：** 英语作为基础能力语言，中文作为 LoRA 适配器
- **理由：** 预训练占比高（70-80%）、可用数据多、模型内部推理更强、语言可插拔
- **⚠️ 论据修正（2026-09-21）：** 原写的"中文 2-3x token"对 **Llama 系** tokenizer 成立，对 **Qwen 系**需打折（Qwen 的 tokenizer 对中文做过专门优化）。此项**待实测**，见 [15-language-plan.md](15-language-plan.md) 第 2.5 节
- **状态：** 已定
- **影响：** 数据配比、**训练顺序（先英文后中文，见 D18）**、部署时的适配器切换

- **日期：** 2026-09-21
- **决策：** 在模型内部实现双通路 + 交叉注意力，**不做**外部调度系统
- **理由：** 用户明确要求"底层的，数据交换和同时运行，而不是外部系统程序"
- **状态：** 已定

## D05 · 4B 而非 8B

- **日期：** 2026-09-21
- **决策：** 先用 4B 双通路验证架构，暂不上 8B
- **理由：**
  1. 8B 双通路 = 16B，4060 8GB 装不下
  2. 4B 双通路 ≈ 8B 单通路的计算成本，但多出架构创新
  3. 最大风险是"架构是否有效"，不是"模型够不够大"
  4. 4060 能训能跑，迭代快
- **状态：** 已定（维度写成可配置，便于未来升级）
- **影响：** 质量天花板为 4B 级（RP 场景约为 8B 的 90%）

## D18 · 训练顺序：先纯英文，后中文 LoRA

- **日期：** 2026-09-21
- **决策：** 训练严格按 **阶段 0/1（纯英文）→ 阶段 2（中文 LoRA 叠加在英文 RP 基础之上）→ 阶段 3（其他语言，可选）** 执行
- **理由：**
  1. **模式只教一遍** —— 状态跟踪、角色一致性、语气控制等行为模式与语言无关；英文阶段学会后，中文 LoRA 只需学"用中文表达同一套模式"，数据量可降至英文阶段的 30-50%
  2. **省 LoRA 容量** —— 中英同训会让有限容量被"中文怎么说"吃掉（基座本来就会中文），两边都学不好
  3. **数据生态** —— 英文 RP / 对话数据在数量与质量上明显优于中文
  4. **可升级** —— 各语言独立适配器，可单独重训 / 回滚，互不干扰
- **配套要求：**
  - 英文阶段数据必须做**语言过滤**（不含中文），防止地基不纯
  - 中文 LoRA 数据**必须含中英混杂样本**（英文人名 / 地名 + 中文对话）
  - 中文 LoRA 数据量起步按英文阶段的 30-50%，比例本身需消融实验确定
  - 必须有**固定中文评测集**与**跨语言回归测试**（中文上线后英文不得下降）
- **状态：** **已定**
- **影响：** 训练排期、数据准备顺序、里程碑 2 的阶段划分、部署时的适配器切换
- **详见：** [15-language-plan.md](15-language-plan.md)

## D19 · 英文优先前提下是否重选基座（待定）

- **日期：** 2026-09-21
- **背景：** 用户指出"要先英文的话，可以换模型"。D16 之所以选 Qwen3-VL-4B，理由之一是"中文优秀"。既然中文推迟到阶段 2，这条理由的分量下降，基座选择重新开放
- **硬约束（决定性）：** **LoRA 教不会一门基座不认识的语言。** 中文适配器能否成立，取决于基座本身还剩多少中文表征。因此"换模型"只能在 **"英文更强 且 中文没被丢干净"** 的区间里选
- **候选短名单（基于离线知识，2026 年新模型未联网核查）：**

| 候选 | 英文 | 中文保底 | 多模态 | 许可 | 4B 双通路 | 结论 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| **Qwen3-VL-4B-Instruct**（现选） | 强 | ✅ 强 | ✅ | Apache-2.0 | ✅ | **保持** |
| Gemma 3 4B | 强（创意写作略优） | ⚠️ 弱 | ✅ | Gemma Terms | ✅ | 备选 |
| InternVL3 系 4B 级 | 强 | ✅ 中上 | ✅ | Apache / MIT | ✅ | 观察 |
| Phi-4-multimodal 5.6B | 强（偏推理） | ❌ 很弱 | ✅（含语音） | MIT | ⚠️ 偏大 | 不推荐（RP 弱 + 中文无保底） |
| 纯文本英文基座（Llama-3.2-3B 等） | 强 | ❌ 基本没有 | ❌ | 社区许可 | ✅ | 不推荐（违反 D14，且中文阶段会崩） |
| 从零预训练英文小模型 | —— | ❌ | —— | —— | —— | 不在范围 |

- **换不换的判断标准（按顺序测）：**
  1. 英文 RP 主观对比（同 prompt、同采样参数、4-bit）
  2. 中文**未微调**时的基础能力（能否流畅对话）—— 决定中文 LoRA 是否还有意义
  3. 许可是否允许个人长期使用与修改
  4. 4B 级（双通路显存约束）
- **倾向：** **保持 Qwen3-VL-4B。** 英文优先并不削弱它的优势，而它的中文保底是第二阶段的地基。只有实测显示它在英文 RP 上明显弱于同尺寸候选时，才值得付出"中文保底"这个代价去换
- **状态：** **待定**（等英文 RP 对比实测）
- **关联：** D02 / D03 / D16 / D18；[15-language-plan.md](15-language-plan.md) 第 2.6 节

## D20 · 蒸馏教师模型：按环节分配，分两档

- **日期：** 2026-09-21
- **决策：** 不采用"一个教师包打天下"，而是**按蒸馏环节分配教师**，并分两档使用：

| 档 | 模型 | 用途 |
|:---:|------|------|
| **A 档（自部署，主力）** | **Qwen3.8-27B**（Apache-2.0，27.8B，多模态）、**Qwen3.6-35B-A3B**（Apache-2.0）、**GLM-4.7-Flash**（MIT，31.2B） | RP 风格、通用对话、工具调用 |
| **B 档（租用 / API，仅难样本）** | **GLM-5.3-Flash**（MIT，321B MoE，1M 上下文）、DeepSeek-V4-Flash（MIT，304B） | 状态跟踪、记忆写入/读取 |

- **理由：**
  1. **只能做输出蒸馏** —— 学生词表 151936，Qwen3.8 系词表 248320，**logits 蒸馏不可行**；输出蒸馏对词表不一致不敏感
  2. **同族优先** —— Qwen3.8-27B 与学生同族，风格先验与对话习惯最接近
  3. **教师不宜过大** —— 学生 4B，教师 27B-36B（7-9 倍）是甜点区；千亿级巨兽输出学生学不动
  4. **强模型当裁判不当老师** —— 闭源榜首模型用于质量筛选与打分，避免条款风险与"学不动"
  5. **看 Slop 分** —— EQ-Bench Slop 越低越好，教师套路化会传染给学生
- **核查结果（2026-09-21 联网）：** 完整表格、数据来源与四条实操原则见 [08-data.md](08-data.md) 第六·补节；原始页面缓存在 `reports/web-*.txt`
- **已排除：** Muse-Glimmer-30B（Meta，30B 多模态，创意写作 Elo 1790）—— 实测**区域锁定**，不可用
- **状态：** 已定（教师清单可能随榜单更新，届时按同流程重新核查并追加新决策）
- **影响：** 蒸馏成本（$5-20）、云 GPU 选型（单张 24GB 卡起步）、数据管线需支持"多教师 + 按环节路由"

## D22 · 混合蒸馏配方 v2：四层教师 + 无审查层

## D26 · S2 速度归因：瓶颈在 bitsandbytes 4-bit kernel，速度问题独立立项

- **日期：** 2026-09-21
- **背景：** S2 基线实测 4-bit 只有 **10.6 tok/s**，远低于路线图里程碑 2 的 60+ tok/s 目标。做了归因诊断（[reports/s2-speed-diagnosis.md](../reports/s2-speed-diagnosis.md)）。
- **实测证据（已核查）：**
  1. 实测显存带宽 **234 GB/s**；4-bit 权重 2.01 GB → 理论上限 **~116 tok/s**；实际 10.6 tok/s = **约 9% 效率**
  2. 算子级：fp16 `Linear` 打满带宽（234 GB/s）；bnb `Linear4bit` 只有 **47 GB/s**，**比 fp16 还慢 1.26 倍**（4-bit 权重本该快 4 倍）
  3. bnb 官方自检 `python -m bitsandbytes` 报 SUCCESS，但 `lib.get_compute_capabilities()` 报 `CPU-only version` → **CUDA 符号不可用，执行落在回退路径**
  4. 6 个 CUDA 版本覆盖、`PATH` 前置、`add_dll_directory`、关 double-quant、换 `fp4`、去掉 `device_map` —— **全部无效**
  5. **fp16/bf16 上限只有 ~29 tok/s，8-bit 上限 ~58 tok/s** → 60+ tok/s 目标**必须**靠 4-bit 级有效位宽
- **决策：**
  1. **S2 基线数字按"当前配置的实测值"落盘并冻结**（4-bit 10.64 tok/s / 8-bit 4.91 tok/s / 峰值显存 2.79 GiB），**不因速度不达标而重测**。这组数字就是"待超越的基准"。
  2. **速度问题独立立项，不阻塞 S3。** S3 的验收只测**正确性 + 显存 < 7GB**，不测速度。
  3. **确立项目级结论：量化不是"优化项"，是达成 60+ tok/s 的必要条件。** fp16 在这张卡上上限 29 tok/s，物理上不可能达标。
  4. **显存结论：** 4-bit 峰值 2.79 GiB，双通路（+约 2 GB）在 D17 的 7GB 预算内是安全的。
- **候选路径（待用户选择，本决策不预选）：**

|:-:|------|------|------|
| A | GGUF + llama.cpp（HANDOFF 原定备选） | 4B Q4 通常 60-90 tok/s | 失去 PyTorch 计算图 → **S3 双通路无法在其上验证**，只能作速度参照 |
| B | 继续修 bnb（换版本 / 源码编译 Windows 轮子） | 修好即约 5x → 55-65 tok/s | 不确定；可能要装 MSVC + CUDA Toolkit |

## D27 · S2 速度归因**更正**：瓶颈是 CPU 算子派发，不是 bnb kernel

- **日期：** 2026-09-22
- **背景：** **D26 的技术归因是错的。** 用户转达了另一位模型基于 D26 给出的"bitsandbytes 静默回退 CPU"诊断，据此重新核查，结论从根上不同。按 AGENTS.md「只追加」规则，D26 原文保留，本条**取代其技术判断部分**（D26 的流程性决定全部继续有效）。
- **已核查的反驳证据：**
  1. `cextension.lib._lib` 就是 `libbitsandbytes_cuda124.dll`；`cgemm_4bit_inference_naive_fp16` / `cquantize_blockwise_fp16_nf4` / `cdequantize_blockwise_fp16_nf4` 均在导出表中
  2. `get_compute_capabilities` **根本不在该 DLL 导出表里**；bnb 的 `BNBNativeLibrary.__getattr__` 对**任何**缺失符号都返回同一句硬编码 "CPU-only version"，**是误导性文案，不是加载失败**
  3. profiler：`bitsandbytes::gemm_4bit` Self **CUDA** = 14.964 ms / 200 次（CUPTI 只统计设备端 kernel）
  4. `Linear4bit(2560,2560)` bs=512 → **319.6 µs = 21.0 TFLOPS**，CPU 回退不可能
  5. **决定性：** `CPU enqueue-only 76.92 ms/step` vs `wall 77.02 ms/step` → **GPU 忙 ≈ 0.10 ms，模型 100% CPU 发射受限**
  6. 重新 profile：bnb gemm **17.1%** / attention **4.0%** / **eager 逐元素与拷贝 78.9%**；约 **8000 次 kernel 启动/token**，平均 9.6 µs/次
  7. 单算子 CPU 开销最贵的是 bnb 自己：**83 µs CPU/次 × 252 次 = 21 ms/token**（Python 派发开销，非 kernel 时间）
- **已实测并排除的修法：** `torchao` int4（152 µs，比 bnb 慢 2.2x）、`torchao` int8（123.8 µs）、transformers 官方编译入口（被 `Bnb4BitHfQuantizer.is_compileable=False` 跳过）、自写前向 + `torch.compile` default（1.70 tok/s，慢 7x）、`reduce-overhead`/CUDA graphs（0.21 tok/s，慢 60x）
- **新的环境事实（已核查）：** `triton-windows 3.2.0.post21` 与 torch 2.6.0 兼容可用（`3.8.0` 不可用）；但 **Triton 可用 ≠ `torch.compile` 可用**（见上）。缓存目录必须显式设为 H 盘（`TRITON_CACHE_DIR` / `TORCHINDUCTOR_CACHE_DIR`）。
- **正面副产品（对 S3 直接有用）：** 自写的逐层精简前向与 HF 官方前向**数值完全一致**（`max|diff| = 0.0000`，argmax 相同）→ 验证了 **"自写 `nn.Module` 组织 forward"** 这条 S3 起步路线可行。
- **决策：**
  1. **D26 的技术归因作废**，以本条为准。D26 的流程性决定**全部保留有效**：S2 基线冻结、速度独立立项不阻塞 S3、量化是必要条件、显存结论。
  2. **速度障碍重新定义为"算子派发开销"，不是"kernel 效率"。** 因此**换量化后端（torchao / AWQ / Marlin）不再是候选路径** —— 已实测无效。
  3. **60+ tok/s 的两条现实路径（待用户选择）：**
     - **路径 ①：自写精简前向** —— 融合 RMSNorm、消除冗余 dtype 转换、必要时用 Triton 手写融合 kernel。**与 S3 天然合流**（S3 本来就要自写双通路 forward）。不换运行时，风险最低。
     - **路径 ②：换运行时** —— WSL2 + Linux（自带 Triton + flash-attn2 + 更成熟的 `torch.compile`）或 GGUF/llama.cpp（**只能当速度参照，无法验证双通路**）。
  4. **建议顺序：** **先做 S3（路径 ① 的前向骨架顺带产出）→ 拿到骨架后再评估是否需要路径 ②。** 不单独为速度开一轮。
- **状态：** 已定（1、2、4）；**待用户选择**（路径 ①/②）

## D28 · S3 双通路骨架完成：门控关闭与基线逐位一致

- **日期：** 2026-09-22

  1. **层切分**：共享前段 6 / 双通路段 24 / 共享后段 6（共 36 层），交叉点每 4 层一处（相对层 0/4/8/12/16/20）

  4. **两条通路各自持有权重**：通路 0 复用 HF 原层，通路 1 深拷贝 —— 这才是双通路的真实显存代价
  5. `norm_impl` 双实现：`exact`（与 HF 逐位一致，**验收用**）/ `triton`（单 kernel，**速度用**，差异 ≤ 1 fp16 ulp）
- **开发中踩到的两个 bug（写进报告备查）：**
  1. `LeanRMSNorm` 权重建成了 fp32，导致 `exact` 反而与 HF 不一致；`triton` 因 kernel 内显式 `.to(fp16)` 而"侥幸"逐位一致 —— **"某个实现看起来更接近参考"不能当作它正确的证据**
  2. 自写前向的 `position_ids` 从 0 开始编号，导致 **prefill 对、decode 错** —— **验收必须同时覆盖 prefill 与 decode**
- **决策：**
  1. **S3 验收通过**，双通路骨架成立。**下一步进 S4（记忆最小实现）**，与速度路径并行。

  3. **本决策不改变 D17 的 7GB 预算，也不改变"先英文后中文"（D18）与"暂不训练"的禁区。**

- **日期：** 2026-09-22
- **背景：** D28 完成后，Nova 单通路 63.0 ms/token、双通路 109.9 ms/token，仍严格受限于 CPU 算子派发（D27）。原计划的下一步是"自写 Triton NF4 GEMV 替掉 bnb"。
- **先做的测量（已核查）：** `src/diagnostics/microbench_op_cpu.py` 实测本机**单次 kernel 启动约 13.5us CPU** —— 连 `x * 2.0` 都要 15.96us，且开销**严格线性**（64 个 mul = 887us）。Nova 每 token 约 6500 次算子调用 × ~9.6us ≈ 62ms。**瓶颈不是"算得慢"，是"发不动"。**
- **实测结果（已核查）：** 把**整步解码**捕获成一张 CUDA Graph 后：

| 配置 | 层数 | tok/s | ms/token | 峰值显存 |
|------|:---:|:---:|:---:|:---:|
| HF 基线 | 36 | 13.24 | 75.5 | 2.73 GiB |
| Nova 单通路 eager | 36 | 15.87 | 63.0 | 3.04 GiB |
| **Nova 单通路 + CUDA Graph** | 36 | **61.84** | **16.2** | 3.09 GiB |
| Nova 双通路 eager | 60 | 9.10 | 109.9 | 4.57 GiB |
| **Nova 双通路 + CUDA Graph** | 60 | **40.26** | **24.8** | 4.64 GiB |

  1. **单通路 4.7x（对 HF 基线）、双通路 3.0x**；`pytest tests -q` → **12 passed**
  2. **正确性：单通路 24/24、双通路 24/24 个 token 与 eager 解码完全相同**；逐步 logits 偏差 3e-2~8e-2（fp16 舍入级）
  3. 显存 4.64 GiB，仍满足 D17（< 7GB）
  4. **路线图的 60+ tok/s 目标，单通路已达成（61.84）**；双通路 40.26 尚差，缺口在 bnb 的 4-bit 路径
- **关键实现决定：**
  1. **`StaticKVCache`**：预分配定长 KV，用 `index_copy_` 原地写槽位（`DynamicCache` 的 `torch.cat` 形状每步变，无法进图）；`pos` 必须放在 **GPU** 上
  2. **加性 mask 表**：预计算 `[max_len, max_len]`，图内一次 `index_select` 取当前行 —— 注意力长度恒定才能进图
  3. **整步（含 argmax 与写回输入缓冲、`pos+1`）全在图内**，CPU 每 token 只发一次 `replay()`
  4. **replay 必须在 `torch.inference_mode()` 内**（图内有原地写入）
  5. `LeanAttention.gqa_in_sdpa = True`：有 mask 时也走 SDPA 的 GQA，避免每层每 token 白拷 8MB
- **开发中踩到的 bug（已修，已固化成测试）：** `prefill()` 把 `input_ids` 填成**最后一个 prompt token**，而 `pos` 已指向 `n` —— 图的第一步会在位置 `n` 上把它**再算一遍**。单通路"看着 16/16 一致"纯属巧合，双通路暴露成 17/24。修法是填**第一个生成 token**。
- **剩余开销分解（已核查 · 局部图测量，单通路 17.0ms）：** 36 层 **12.90ms（75.9%）** / lm_head **3.12ms（18.3%）** / 其它 1.0ms。其中：
  1. **lm_head 已打满带宽**（0.78GB fp16 / 3.12ms = 250 GB/s），无优化空间
  2. **36 层是主要缺口**：4-bit 权重 1.23GB，带宽下界 5.3ms，实测 12.90ms → **2.4x**
  3. 原因：**bnb 的 `Linear4bit` 在 M=1 时没走 packed 4-bit GEMV**，而是 dequant 到 fp16 workspace + cublas（单算子 GPU 耗时 29.2us vs fp16 的 27.9us，几乎相同）
- **决策：**
  1. **CUDA Graph 解码成为 Nova 的默认推理路径**；`norm_impl="exact"` + eager 路径继续保留，作为"逐位一致"验收的基准。
  2. **速度路径 ① 优先级重排**：① **自写 Triton NF4 dequant+GEMV 替掉 bnb**（36 层 2.4x 缺口）→ ② 量化 lm_head → ③ 融合 RoPE / 去冗余拷贝 → ④ 融合注意力。
  3. **本决策不改变 D17（< 7GB）、D18（先英文后中文）与"暂不训练"的禁区。**
- **状态：** 已定
- **关联：** [reports/s3-graph-decode.md](../reports/s3-graph-decode.md)；承接 D27/D28；[10-risks.md](10-risks.md) 风险 15

## D30 · 速度路径 ① 结案：自写 Triton NF4 GEMV 证伪；lm_head 换 4-bit 得 −2.0 ms/token

- **日期：** 2026-09-22
- **背景：** D29 第 2 条把速度路径 ① 定为"自写 Triton NF4 dequant+GEMV 替掉 bnb"（依据是 D27 测到 bnb 在 M=1 时没走 packed 4-bit GEMV、36 层有 2.4x 缺口）。
- **已核查（全部用 CUDA Graph 计时 = 纯 GPU 时间）：**
  1. **7 个投影形状无一胜出**：自写 kernel 比 bnb 慢 **1.31x ~ 2.75x**（q_proj 1.43x / k·v_proj 2.73~2.75x / o_proj 1.98x / gate·up 1.31~1.32x / down 2.01x）。
  2. **bnb 已经几乎打满带宽**：36 层 4-bit 权重 2.04 GB，DRAM 下界 8.20 ms（249 GB/s 实测）；bnb **9.79 ms（距下界 1.19x）**，自写 **16.28 ms（1.99x）**。→ 留给"更快的 GEMV"的空间本来就只有 19%。
  3. **36 组 launch 参数（block_n × num_warps × num_stages）没有一个快过 bnb。**
  4. **更激进的结构更差**：`tl.dot`/MMA 848us vs bnb 234us；`tl.gather` 直接编译失败；全宽 BLOCK_N 568us；fp16 码本 394us。
  5. **端到端**：`--quant nf4` **28.8 ms/token** vs `--quant bnb` **16.0 ms/token**（单通路 36 层，图解码）。
- **真正的收益（已核查）：** `lm_head` 复用 fp16 `embed_tokens.weight`（778 MB）实测 **3.11 ms**，**确实已打满 250 GB/s** —— 但换 4-bit 后**要搬的数据只剩 1/4**，bnb `Linear4bit` 实测 **1.02 ms（3.05x）**。
  - 单通路 **16.0 → 14.0 ms/token**（62.35 → **71.34 tok/s**）
  - 双通路 **24.8 → 22.7 ms/token**（40.38 → **43.99 tok/s**）
  - 代价 **+0.187 GiB**（4-bit 副本 219 MB）；峰值 **4.83 GiB**，D17 预算内。
  - 精度：贪心解码 **24/24、32/32 个 token 与 fp16 一致**。
- **决策：**
  1. **速度路径 ① 结案，不再投入。** 自写 NF4 kernel 保留在 `src/nova/quant.py`（`convert_to_nf4` 仍可用，作证伪证据与参考），但**不是默认路径**；默认继续用 bnb。
  2. **`enable_lm_head_4bit()` 成为 Nova 的默认配置** —— 这是 D29 第 2 条里的"路径 ②"，本决策落地。
  3. **取代 D29 第 2 条的路径排序**：原 ① 作废；余下优先级为 **③ 融合 RoPE / 去冗余拷贝 → ④ 融合注意力**。
  4. **认知修正（并入风险）：** 「已打满带宽」只说明**访存效率**没得优化，**不等于没得优化** —— 降位宽改的是**数据量**，两者正交。
  5. 不改变 D17（< 7GB）、D18（先英文后中文）与"暂不训练"的禁区。
- **状态：** 已定
- **关联：** [reports/speed-path1-nf4-gemv.md](../reports/speed-path1-nf4-gemv.md)；**取代 D29 第 2 条**；承接 D26/D27

## D31 · S4 记忆最小实现：L0 精确 KV + 无训练键值联想，20 轮后 8/8 取回

- **日期：** 2026-09-22
- **背景：** 路线图里程碑 1 的最后一块（[HANDOFF.md](../HANDOFF.md) 第七节）。验收标准：**第 1 轮写入 → 第 20 轮取回；存盘重启后仍可取回**。
- **已核查（验收）：**
  1. **8/8 全对**：6 条事实 × 8 个问题（含 3 个改写问法），写入后隔 20 轮无关对话（608 token）。
  2. **对照与因果**：不注入（`off`）→ **0/8**，表现是反问或编造；故意注入另一条（`swap`）→ **0/8**，原答案不再出现。答案**来自注入内容**。
  3. **存盘重启**：`--phase write` 与 `--phase ask` 是**两个独立进程**，只通过 `.safetensors` 传递 → 8/8。
  4. **注入与真实 prefill 逐位一致**：逐位最大差 `0.000e+00`（60 个 cache 槽位 × K 与 V）。
  5. **显存** 峰值 **5.17 GiB**（双通路 + 记忆 + max_len=1024），D17 预算内。
- **已核查（开销，608 token 历史 + 17 token 当前轮，双通路 triton）：**
  - **检索 / 基线前向 = 0.94–0.98x**（与时钟无关的比值）→ 取 Q 要跑**一次完整无 cache 前向**，成本 ≈ 再 prefill 一遍。
  - 打分 **40–90 ms**；**注入 ≈ 0**（三次独立测量 −41 / −40 / −12 ms，逐轮交替取差值中位）。
  - 记忆体积 **240 KiB/token**（无损、不压缩），6 条 = 70 位置 = **16.41 MiB**。
  - ⚠️ 连测 7 轮会把笔记本 GPU 从 2160 MHz 压到 ~870 MHz、94 W → 35 W，**同一条件耗时翻倍**。速度数字一律带 `clocks.sm`。
- **决策：**
  1. **S4 落地为 [docs/09-speculative.md](09-speculative.md) 的 L0「精确 KV」层**，不是 [docs/03-memory-system.md](03-memory-system.md) 里那套 `[128, 2560]` 记忆令牌。后者配 `[128, 512]` 独立键，是**要训练的**写入器 / 读取器（模型得先学会"什么值得记""怎么生成记忆令牌"），属**里程碑 2**。
  2. **键 = 模型自己的 Q/K，不新增任何投影层、不训练**。这是 D09「记忆模块与语言模型解耦」在 L0 的自然形式：既然没有新增参数，就不存在"记忆模块被训练带动而漂移"。
  3. **寻址 = 按注入后真实位置的 `Q·K` 注意力质量**（softmax 汇总到每条记忆）。三条硬性要求都是实测逼出来的：**必须旋转到注入后的真实位置**（pre-RoPE 裸余弦对 6 条候选全部 > 0.8，几乎不区分内容）；**必须用 softmax 质量**（减掉键的公共加性偏移）；**查询取问题那句话的末尾 4 个 token**（取 prompt 末 4 个拿到的是 `<|im_start|>assistant\n`，无内容；整句取平均 8/8 掉 7/8）。
  4. **打分默认 `frame="alone"` + 按 token 数归一 + 不标准化**（6 条 × 8 问，12 组配置全扫）：`alone`+归一+不标准化 **8/8**；不归一 7/8；`stack` 2/8（真实推理只注入 top-1，打分坐标系必须与之一致）；标准化在大候选集上反而变差（4/8）。
  5. **记忆插在"当前轮之前"（`place="turn"`），不插最前面**。`place="front"`（文档原写法）在 20 轮历史下寻址退化到 1/3，**且生成质量崩**（复读"今天多云转晴"）—— RoPE 长距离把 `Q·K` 抹平了。**这条推翻 docs/03 里"拼在上下文最前面"的默认写法。**
  6. **检索逻辑单点实现**（`MemorySession.rank()`），`prefill` 与测试都走它。教训：第一版测试自己手搓了一遍打分、忘了截末尾 4 token，命中率立刻从 8/8 掉 7/8 —— 同一套逻辑写两份必然漂移。
  7. **表示空间冻结（D09）落地**：文件带 `schema_digest`（`cac396b8…`）与 `model_fingerprint`（`3354283f9349…`），不匹配**拒绝加载**（`MemorySchemaMismatch`），宁可"想不起来"也不要读串味；`allow_foreign` 才放行。
  8. **不碰禁区**：本阶段**没有训练**任何参数，不引入外部检索 / 数据库 / agent 框架（D06），记忆是模型自己的 K/V 张量（D07）。
- **已知边界（不要当成已解决）：** 无损不压缩（随区间线性增长）；键未训练，区分度是**实测**而非设计保证；**LoRA / 微调会让 K/V 空间漂移**，匹配质量的衰减**待实测**（里程碑 2 必测）；通路 0/1 各存一份（门控关闭时逐位相同，已核查 → 2× 冗余）；检索不能跨轮复用。
- **下一步（按收益排序，尚未实施）：**
  1. **把检索从 ~1x prefill 降到 ~0**（**推测**可行）：取 Q 只需要问题那几个 token 的 Q，而 **pre-RoPE 的 Q 与位置无关** —— 生成时反正要 prefill 历史，可复用那份 cache 的隐状态，只为当前轮 17 个 token 单独取 Q。每轮省下近一次完整前向（≈950 ms @低时钟 / ≈430 ms @高时钟）。
  2. `--dedup` 只存一条通路，省一半记忆体积。
  3. 把 `scores` 的逐条旋转向量化。

## D33 · 长上下文瓶颈是注意力后端而非 KV cache：一个开关换来 4 倍长度

- **日期：** 2026-09-22
- **背景：** 用户提出"优化到让 4060 8GB 能跑满 260K 上下文，再测信息过载时能否注意到重点"。开工前先量了当前天花板，结果发现瓶颈不在原先设想的地方。
- **已核查（诊断脚本见 [reports/long-context-attention.md](../reports/long-context-attention.md)）：**
  1. **瓶颈是注意力后端，不是 KV cache。** 本机 torch 2.6.0+cu124 **没有编译 flash attention**；mem-efficient / cuDNN 两个融合内核**都要求 Q/K/V 头数相同**；而我们是 GQA（32 Q / 8 KV）配 `enable_gqa=True` → SDPA **退回 math 后端 → 实体化 O(n²) 的 fp32 分数矩阵**。3665 token 的 prefill 峰值 **8.80 GiB**（超过显卡物理 8188 MiB，开始换页，耗时 29.1 s），7291 token 直接 OOM。而按 KV cache 算只该占 1.41 GiB。算术验证：`32 头 × 3520² × 4 字节 × 2 张 ≈ 3.2 GiB`，与实测缺口吻合。
  2. **改一行就解决**：`gqa_in_sdpa = False`（进 SDPA 前先 `repeat_kv` 展平成 32 头）。头数相同后融合内核可用。**同一轮内**对比：1749 token **2.1x**、3012 token **2.5x**、4096 token **4.1x**（6.76 GiB → 3.26 GiB）；长度 ×4（1749 → 7146）峰值只从 3.15 涨到 3.53 GiB，**O(n²) 消失**。
  3. **数值正确性已过**：两边都钉 math 后端时 `repeat_kv` 与 `enable_gqa` **逐位一致（0.000e+00）** → head 映射正确；两者对手写 fp32 参考的相对误差相同（4.07e-04）→ 精度等价；生成层面**贪心 32/32 token 一致**（项目既有标准：lm_head 4-bit 是 24/24、32/32）。
  4. **新天花板：~14–15K token**（单通路 · fp16 KV · KV cache 按长度分配）。14363 token 健康（6.47 GiB / 9.36 s），21615 token 峰值 8.50 GiB、prefill **375.9 s**（换页断崖）。
  5. **信息过载下的选择性没有退化（已核查）**：4 条**同形干扰事实**（格式相同、只有地点与号码不同）埋在不同深度、各问一次 —— **1894 / 3665 / 7291 / 12728 token 全部 4/4 答对，零挑错**，峰值 6.67 GiB，prefill 6.8 s（clocks.sm 2340–2460 MHz）。
- **决策：**
  1. **`gqa_in_sdpa` 默认改为 `False`**（走融合内核）。理由是 math 回退是**退化路径**：fp32、O(n²)、慢 2–4x，且在 3.5K token 就到顶 —— 不能作为跑在自己显卡上的产品的默认。
  2. **把"架构保真度"与"内核 dispatch"拆开测**：`test_gating_off_matches_baseline` 两边钉 `sdpa_kernel(MATH)`（它测的是架构与权重，不该受恰好 dispatch 到哪个内核影响）；新增 `test_fused_attention_agrees_on_tokens` 测展平路径的 token 一致率。`pytest tests -q` → **41 passed**。
  3. **代价如实记：与 HF 的"逐位一致"没有了** —— 原始 logits 会有 fp16 累加级差异（`max|diff| ≈ 1.0`，logits 量级 112，即 0.9%），token 决策一致但数值不完全相同。D28 的"门控关闭逐位一致"今后**必须注明是在 math 后端下**。

## D34 · KV int4 量化：精度在 12.7K 内测不出退化，但 3.46x 的收益一分未到手

- **日期：** 2026-09-22
- **背景：** 承接 **D33 第 5 条的 ①/②**（int4 KV 是唯一"不碰训练就能拿到的 ~4x"）。用户同时给了文献层面的三层提示（①精度损失不均匀、②工程上 dequant 要花算力、③与 S4 记忆的表示空间冲突），并明确要求：**文献条目一律按 `文献引用 / 待实测` 标注，只有我们自己的 needle 数字才作数。**
- **已核查（完整证据见 [reports/kv-int4.md](../reports/kv-int4.md)）：**
  1. **量化方案与记账**：K 按 `head_dim` 每 32 通道一组（K 的离群值是通道级），V 按每个 `(token, head)` 整条 128 维一组（V 的离群值是 token 级）；非对称，`min`/`step` 各存 fp16，两个 int4 打进一个 `uint8`。**fp16 144 KiB/token → int4 41.6 KiB/token = 3.46x**；元数据只占 13.5%。
  2. **量化器本身数值正确**：`tests/test_kvquant.py` **13 passed**（反量化与公式逐位一致、误差 ≤ 组内 `step/2`、分组不受邻组离群值污染、`max==min` 退化无损、分组/打包形状、记账数字）。全套 `pytest tests -q` → **54 passed**。
  3. **`--kv int4` 一开始 0/4 是「接线 bug」，不是精度损失。** 根因：`QuantRoundTripCache.update` 把已写入范围写成 `pos + 1`，而 `StaticKVCache.update` 在**多 token**时会内部转调 `append_prefill` 且 `pos` 不推进 → prefill 时只有第 0 个位置被拷进工作区，1..n-1 留在工作区的 0 上。改成 `pos + n` 后恢复。**决定性线索是一个"本该恒等"的对照组**：`residual=128` 在 15 token 上 `keep == 0`（一个位置都不该被量化）却仍与 fp16 不一致。两条回归测试已入库。
  4. **端到端 needle 逐档零退化**：4 条同形干扰事实、**同一轮内**跑 fp16 与 int4 —— **1894 / 3665 / 7291 / 12728 token 全部 4/4，零挑错，与 fp16 基线逐档相同**（含贴着 D33 天花板的 12728）。
  5. **但误差是真实存在的**（不能解读为"int4 无损"）：真实 K/V 上 K 相对 L2 误差最坏 **11.8%**、误差/step 稳定在 0.48（理论中位 0.5）；**第 0 层 K 的通道离群度 65x**（中间层 4.3–7.2x），该层量化噪声达通道激活的 **55%** —— 用户文献第 ① 条的"离群值"现象**我们复现了**。
  6. **开销（同轮交替取小值，标 `clocks.sm`）**：朴素"先反量化再喂 SDPA" **prefill 1.0–1.5x / decode 2.0–5.0x 每 token**；在 `max_len=18432`（贴近 8GB 物理上限）时 needle 环境实测 prefill 涨到 **8.4x → 25.8x**。**现象已核查；归因标注为 `推测`**（证据：倍数随 `max_len` 而非 `used` 单调涨、峰值 6.87 GiB 贴近 8188 MiB，与 D33 那次 375.9 s 断崖同源；未把"换页"与"分配器碎片"分离）。
  7. **模拟版不省显存**：SDPA 必须吃 fp16，所以"先还原再算"必须有整段 fp16 工作区 —— 显存收益**一点没拿到**，还多 75.5 MiB（36 层共用的那块；早期按层各留一块时峰值 11.8 GiB、prefill 1.2→19.6 s，是"仪器的显存开销伪装成算法慢"）。
- **决策：**
  1. **int4 KV 按"记账 3.46x、精度 12.7K 内无退化、收益尚未到手"记录。** 262144 × 41.6 KiB = **10.4 GiB**，D17 预算内只剩 ~3.8 GiB → **int4 单独还差 ~2.7x**，跨层 KV 共享 / MLA（两者都要训练）仍是必需的。
  2. **暂不写融合 attention kernel。** 先做三件更便宜、更可能改变方案的事：**①细尺子**（干扰项 4→16→64 条同形事实 + 更多档位，现在 4 道题的尺子测不出 10% 量级退化）；**②试 8 位**（约 1.9x 但误差减半、torch 有现成路径，**性价比可能高于 int4**）；**③分组方向对照**（K 改按 **token 维**分组，即每通道一条跨 token 的尺子 —— 第 0 层 65x 离群说明现有分组在首层很吃亏）。**否则会把一套可能要推倒重来的量化方案固化进 Triton。**
  3. **融合核的进场条件：** ①–③ 有结论后再决定；写之前先定死验收 = 与"先还原再算"的注意力输出**逐位或 ULP 级一致**。顺带记：路线 ③"换推理引擎（vLLM/TRT-LLM 的 FP8 KV）"**撞 D06**，排除。
  4. **记忆模块与 int4 的表示空间规矩（用户第 ③ 点，本项目定死）：** **记忆一律按 fp16 存**（它是"原话"，L0 层承诺无损）；**int4 只是运行时 cache 的存储格式**；记忆注入 cache 时**按注入那一刻的 cache 格式量化**。因此 **D09 的冻结判据不变**（记忆之间比的是 fp16 张量，int4 不参与一致性判断）。将来若真要"记忆也存 int4"，**必须新开决策并重测取回率**，不许顺手改。
  5. **文献条目一律 `文献引用 / 待实测`**，逐条状态见报告第八节；其中"长上下文误差累积、128K 才明显"**我们只测到 12.7K、未测出退化**——这不构成对文献的反驳（样本小、尺子粗）。"FP8 几乎无损且是工程默认"这一条**待实测，且被提到 int4 之前的评估位置**。
  6. **不碰 D06 / D07 / D09 / D17**；D13 / D14 / D18 无关。
- **状态：** 已定
- **关联：** [reports/kv-int4.md](../reports/kv-int4.md)；**承接 D33 第 5 条 ①/②**；受 D17 约束；D09 的判据在本条被显式重申

## D35 · 拆掉 O(n²) 掩码表 + 容量分桶：decode 少搬 48–60%（并推翻"重捕爆显存"）

- **日期：** 2026-09-22
- **决策：**
  1. **解码器不再预分配 `(max_len, max_len)` 的加性掩码表**，改成图内即时构造一行
     （`GraphDecoder._mask_row`）。常驻从 `max_len²×2` 降到 `8×max_len`（arange）
     + 图内 `2×max_len`（掩码行）：65536 档 **8.00 GiB → 512 KiB + 128 KiB**，且**逐位一致**。
  2. **KV 容量按桶分配**（`BUCKETS = 2070/4096/8192/16384/32768/65536`），新增
     `bucket_for()` / `GraphDecoder.for_length()` / `GraphDecoder.grow()`（跨桶搬家 + 重捕）。
     调用侧的**推荐写法是 `for_length`**，而不是随手给一个巨大的 `max_len`。
  3. **`capture()` 的图内存池默认 `pool="off"`（不共享）**。旧结论"每题重捕 → 7905 MiB 崩溃"
     **被实测推翻**：真凶是图没被正确释放；共享池不是必需，反而会踩 PyTorch 的裸 assert。
- **理由（实测）：**
  - **拆墙**：65536 档的掩码整表 8.00 GiB 是"上下文上限"的第一堵墙（比 KV cache 更早爆）。
    不拆它，E2（滑窗）的 32K/64K 档与 E5（干扰 64 条）根本开不了场。
  - **选桶**：`used=2048` 时 **139.1 → 56.1 ms/token（省 59.7%）**；`used=7291` 时
    138.7 → **71.2 ms/token（省 48.6%）**（单通路 triton，同轮交替两遍取小，`clocks.sm 2460`）。
    判据成立：耗时**只随 `max_len` 走**，几乎不随 `used` 走（2048 与 7291 同 max_len 同耗时）。
  - **不改结果**：`_mask_row` 与旧表逐位一致；窄桶 / 搬家后的贪心 token 与宽桶**逐个相同**（测试钉住）。
  - **重捕**：三种池策略的逐轮 allocated 基本平；跨桶重捕的增量**正好等于**多出来的 KV 容量
    （2026×144 KiB = 291.7 MiB / 4096×144 KiB = 576 MiB）⇒ 搬家不漏，峰值 4.33 GiB < D17。
- **遗留（本轮未解决）：**
  - **64K 档仍装不下**：fp16 KV 在 65536 是 9.00 GiB ⇒ 必须靠 **E2 的滑窗层**。
  - decode 的**固定地板 ~59 ms/token**（`max_len=2070` 时 KV 只占 ~1 ms）与 prefill 的
    O(n²) 算力墙（12.7K=6.8 s → 32K≈45 s → 64K≈180 s）都一分没动，属速度路径 ③/④ 与 E4。
  - 逐轮 **+8.1 MiB** 的缓慢增长（来源未定位，实验循环跑到 100 轮量级前需重测）—— **待实测**。
  - 共享池 assert（`CUDACachingAllocator.cpp:2225` 裸 assert）只在 pytest 全量跑中触发、
    5 种脚本调用序列都复现不出 ⇒ 触发条件是**推测**（依赖分配器状态），处置是**默认绕开**。
- **状态：** 已定（**推翻** `reports/kv-int4.md` 里"重捕就爆显存"的归因）
- **关联：** [reports/decode-mask-bucket.md](../reports/decode-mask-bucket.md)；受 D17 约束；
  是 D33/D34 之后所有长上下文实验（E1–E6）的前提

## D36 · 记忆路由结案：段级静态代表 K 不 adopt；`top-‖K‖` 判断被证伪

  2. **`top-‖K‖` 明显差于 `mean-K`（侧会话"用范数最大、不要用平均"被证伪）**：

## D37 · 滑动窗口结案：不 adopt；"少看 token"会毁检索，且 prefill 反而更慢

- **日期：** 2026-09-23
- **决策：** **不采纳滑动窗口**（局部层 ring + 少数全局层）。260K 的方向回到

  1. **质量门控未过**：7.3K 与 14.5K 上下文上，每 4 层 1 全局 + W∈{1024,2048,4096} **全部 0/4**
     （全量基线 4/4）；32K 档 0/4。
  2. **不是单纯的"截断"**：W=8192（盖住整段 7.3K）时 **4/4** ⇒ 实现没问题；

  3. **提高全局层比例会把"答不出"变成"答错"**：每 2 层 1 全局 + W=4096 → 1/4 正确、**3/4 挑错**

  4. **滑窗下的 S4 记忆取回 7/8 → 5/8**（3710 token 上下文，注入的记忆掉出局部层窗口）。
  5. **代价方向是反的**：KV 省 40–67%，但 prefill **更慢**（加性窗口掩码把 O(n²/2) 的因果稀疏性
     变成 O(n·2W) 的稠密读）：7.3K 档 5.6 s vs 全量 4.1 s；29K 档 **180.3 s**（同长度因果外推约 35 s，慢约 5x）。
     峰值也没降（7.63 GiB @32K）。
  6. 附带修掉一个真 bug：`prefill` 把 ring 的 `first` 覆盖成 `offset`，
     使 S4 记忆注入路径上局部层窗口被清空（表现是"所有问题都答不出"）；回归测试已入库。

- **理由（实测，`bench_int8_unpack.py`，5 组 block/warps 配置）：**

  | 模式 | 每次读 | 有效带宽 | 相对 232.5 GiB/s 上限 | 同一份 KV 的耗时 vs fp16 |
  |---|---:|---:|---:|---:|
  | `fp16`（基线） | 0.125 GiB | 230.9 GiB/s | 99.3% | 1.00x |
  | **`int8`** | 0.070 GiB | **200.5 GiB/s** | **86.3%** | **0.65x（快 1.54x）** |
  | `int4`（打包） | 0.039 GiB | **53.4 GiB/s** | **23.0%** | **1.35x（更慢）** |

  1. 判据"≥50% ⇒ 有戏"：**int8 86.3% 通过**（五组配置 85.5–86.3%，稳定）。
  2. 判据"<25% ⇒ 结案"：**int4 23.0% 触发**（block 越大越差，16.3–23.6%），
     且**比 fp16 还慢** —— 省下的带宽被 nibble 解包算术吃光。**D30 的教训重演**。
  3. 这条把 D34 的"先别写融合核"推进为"**可以写了，靶子是 int8**"。
- **状态：** 已定（**E4 结案**）

## D38 · KV 格式改选 8 位：int8（K 按 token 维分组）与 fp16 逐题一致

- **日期：** 2026-09-23
- **决策：**
  1. **默认 KV 量化格式改为 `int8` + K 按 token 维分组**（每 64 个 token 一条尺子，`int8t64`），
     **取代 D34 的 int4 默认地位**；int4 退为"需要更激进压缩时的备选"，且**必须先修分组方向**。
  2. **`fp8` 不进默认路径**（精度不占优、记账更差、per-tensor 口径明显更糟）。
  3. 要写融合核，**就写 int8 的核**，不写 int4 的（E4 的靶子随之改变）。
- **理由（实测，真实 K/V 3665 token + needle 8K 档）：**

  | 变体 | K relL2 | K 通道最坏 | 记账 | 4 干扰 | 16 干扰 | 64 干扰 |
  |---|---:|---:|---:|---|---|---|
  | `int4` | 0.0910 | 0.7705 | 3.46x | 4/4 | — | — |
  | `int8` | 0.0063 | 0.0738 | **1.86x** | 4/4 | 13/16 | — |
  | **`int8t64`** | **0.0018** | **0.0037** | 1.91x | 4/4 | **13/16** | **54/64** |
  | `fp8`（per-token） | 0.0143 | 0.0579 | 1.97x | 4/4 | 12/16 | — |
  | `fp16` 基线 | — | — | 1x | 4/4 | 13/16 | 54/64 |

  1. 判据"K relL2 ≤ int4 的一半"：**8 位全部达标**（int8t64 是 int4 的 **1/50**）。
  2. 判据"needle 与 fp16 相同"：`int8` / `int8t64` 在 4 / 16 / 64 三档**逐题一致**（含挑错的那几条）✅。
     `fp8` 在 16 条干扰上少 1 题（单题样本，标**待实测**）。
  3. **D34 第 3 条"K 改按 token 维分组"被验证**：通道最坏误差 0.0738 → **0.0042（18x）**。
  4. prefill 与 fp16 基本同速（3.5–3.9 s vs 3.4–5.4 s），**比"int4 先反量化再喂 SDPA"那条路好得多**；
     int8 的 decode 逐步开销 **待实测**。
  5. 模拟版**仍不省显存**（SDPA 要 fp16 工作区）—— 收益依旧要靠融合核/分块在线 softmax（E4）。

## D42 · int8 融合注意力核落地：ULP 级一致、16K 单层 7.53x；判据补绝对兜底

- **日期：** 2026-09-23
- **决策：**
  1. **采用** `src/nova/kvattn.py` 的 int8 融合解码注意力核（靶子即 D38+D40：int8、K 按 token 维分组）。
     结构：**按 KV 头切**（GQA 不重复读，K/V 每字节只读一次）+ 分块在线 softmax + split-K 合并核。
  2. **精度路径定死**：打分走 **fp16 张量核 + fp32 累加**（q/k 本来就是 fp16，乘积精确）；
     PV 把概率 **拆成 `p_hi + p_lo` 两个 fp16** 各做一次张量核点积。
     **不许**把 p 直接舍成 fp16（实测掉到 70 ULP），**不用** `ieee` fp32 点积（慢 4.6x）。
  3. **验收判据修订（本条的正式记录）**：与「先还原再算」比，
     **逐元素 ≤ 2 ULP 或 ≤ 1e-5 绝对**。原稿"≥99% 逐位相同"**降级为参考统计量** ——
     该比例随元素数单调下降，16K 下必然被击穿，测的是运气不是正确性。
  4. **默认 launch 参数**：`chunk=512`、`num_warps=8`、`num_stages=2`（扫描过 chunk × warps × stages）。
  5. **接进解码路径是下一步**，本步只交付核 + 判据；**还没有 int8 流式 cache，所以还没真省显存**，
     省的是**带宽**（解码的瓶颈）。
- **理由（实测）：**

  | 项 | 结果 |
  |---|---|
  | 合成 K/V（10 长度 × 3 种子） | 全部 **≤ 1.00 ULP**，无元素 > 2 ULP |
  | 真模型 K/V（1894 token，layer 0/18/35） | 1.00 / 2.00 / **31.00 ULP**，超 2 ULP 的 0/0/**6** 个元素 |
  | 真数据超限元素的绝对偏差 | **≤ 3.9e-6**（< 1e-5 兜底）⇒ 三层全部通过判据 |
  | 16K 单层解码（CUDA Graph 重放） | **0.201 ms vs SDPA 1.513 ms = 7.53x**；带宽 156.7 GiB/s = 上限 67.4% |
  | 8192 单层 | 0.081 ms vs 0.761 ms = **9.33x**；193.2 GiB/s = **83.1%** 上限 |
  | 1024 单层 | 0.029 ms vs 0.102 ms = 3.55x（固定开销占比高） |

  1. **超 2 ULP 的根因已隔离**（7 个实验）：打分点积的 **fp32 归约顺序**差异（张量核一次舍 16 个乘积
     vs cuBLAS 的 tiled 归约）在**相消元素**上被放大。核没有引入新误差源：反量化与
     `torch.dequantize_int8` **逐位一致**（242432 元素 0 差异）、张量核确实是 fp32 累加（7.5e-7 相对）、
     p 拆分单独只贡献 3.1e-5、`tl.exp` 差 1.9e-6、Kahan 补偿**没有任何改善**（52→52 ULP）。
  2. **顺手核查了 D34 的观察**：真模型第 0 层 **post-RoPE K** 的通道离群实测 **67.1x**（D34 记的是 65x）✓。
  3. **工程警告**：`tl.dot(..., input_precision="ieee")` 在本核里**只在 `num_warps=4` 下正确**，
     warps=8 时实测输出异常（未归因；最小复现没复现出来）。默认路径不依赖它。
- **状态：** 已定（**第六轮 ①**；核与判据落地，解码路径接入待做）
- **关联：** [reports/kv-int8-fused-attn.md](../reports/kv-int8-fused-attn.md)；`src/nova/kvattn.py`、
  `tests/test_kvattn.py`（21 条）、`src/diagnostics/bench_int8_attn.py`、`probe_kvattn_real.py`；

## D43 · int8 流式 cache 接进解码路径：4K 整步 3.26x、KV 常驻 0.54x

- **日期：** 2026-09-24
- **背景：** D42 把融合核写好了，但**没接进解码路径** —— 卡在两个问题：① `int8t64` 的每组尺子
  要等第 64 个 token 到齐，而解码是一个 token 一个 token 写的；② CUDA Graph 要求形状恒定，
  而"已量化前缀长度"每 64 个 token 涨一次。
- **决策：** 落地 `KVInt8Cache`（`src/nova/kvattn.py`），常驻 = **int8 + 尺子 + 64 槽 fp16 尾部环**。
  三条要点：

  1. **前缀长度走显存标量，不走编译期常量。** 把 `used` / `prefix_groups` 放进 1 元素张量、
     由核内 `tl.load` 读（可行性先单独核查：`src/diagnostics/probe_kvattn_scalar.py`）。
     **理由不是性能，是正确性**：冻结进图的常量每 64 步就过期，而过期不是"变慢"——
     刚写满的组仍被当 fp16 尾部，而环槽已被更新的 token 覆盖 ⇒ **那段历史静默消失**。
     每 64 步重捕是另一条路，但 capture 代价（本机 0.3–1s）远超收益。
  2. **尾部环的掩码下界 = 前缀长度 `_qlen`。** 环里落在 `[0, _qlen)` 的 token 已经在前缀里，
     必须掩掉；少了这条线，那批 token 会被**加权两次**（实测偏差 1.3e-1）。
  3. **解码步内"先写后量化"**：`update()` 把 K/V 写进环槽 `pos % 64` 后，**无条件**把整条环
     量化进第 `pos // 64` 组。部分填充时这一组尺子不对但不会被读到（`_qlen` 只到整组边界）；
     写满那一刻同一层内先写后量化，尺子正好定死。
- **验收（已核查）：**

  | 项 | 结果 |
  |---|---|
  | 与「先还原再算」逐元素一致（合成，L=40…320） | **≤ 4 ULP**（最大 2.44e-4 绝对） |
  | 端到端整步图解码（`clocks.sm 2475 MHz`，桶长 2070/4096/8192） | 1024：46.47→**33.06 ms/token（1.41x）**；2048：69.94→**33.53（2.09x）**；4096：115.68→**35.49（3.26x）** |
  | KV 常驻（同上） | 485→273 / 960→525 / 1920→**1035 MiB（0.539x）** |
  | 峰值显存（4096） | **6.68 GiB** < D17 的 7GB（fp16 同条件 6.59） |
  | 贪心 token 与 fp16 路径 | **4/4 相同**（判据 ≥3/4） |
  | `pytest tests -q` | **114 passed**（原 93 + 流式 17 + 端到端 4） |

- **判据为什么是 4 ULP 而不是融合核的 2 ULP**（已核查）：融合核比的是**同一条**路径的两个实现；
  流式 cache 多了一次**结构性**舍入 —— 前缀走 int8 核、尾部单独走一次 fp16 SDPA，两者按
  `logsumexp` 合并后再舍到 fp16。参考（一次性 SDPA 后舍一次）与它（合并后再舍）不可能逐位对齐。
- **顺手修掉两个坑**（都记在报告第四节）：prefill 按组循环量化（≈4600 次小 kernel）改成每层一次
  → 4096 token 的 prefill **18.2s → 3.65s**；prefill 的加性掩码按头展开（`[1,32,n,hist]`，4096 上 1 GiB）
  改回 `[1,1,n,hist]` 广播 → 峰值 **7.62 → 6.68 GiB**。
- **未做 / 待实测（别当已经做了）：**
  1. **8K 端到端数字待实测**：4096 时 fp16 暂存区（604 MiB）与 int8 常驻同时在场，8K 时两者各 1.2 GiB，
     加模型约 7.0 GiB，试跑进入换页。修法已明确：prefill 按 **64 的整数倍**分块（如 512）、
     暂存区只留当前块 —— 块大小必须是 64 的整数倍，否则分组的尺子会被块边界切坏。
  2. **真模型 K/V 的流式一致性待实测**：合成数据已过，真数据复核（D42 那套）应在流式路径上重跑。
  3. **S4 记忆注入与 `quant="int8"` 不兼容**：`MemoryStore.inject` 直接写 `cache.key_cache[slot]`，
     与 int8 + 环的常驻布局不通用。本轮**没有**解决。
  4. **跨桶 `grow()` 不支持**：`quant="int8"` 下直接抛 `NotImplementedError`（明确报错，不静默算错）。
- **状态：** 已定（**第六轮 ①.5**；解码路径接入完成，8K 与真数据复核待做）
- **关联：** [reports/kv-int8-streaming-cache.md](../reports/kv-int8-streaming-cache.md)；
  `src/nova/kvattn.py`（`KVInt8Cache`）、`src/nova/decode.py`（`quant=` 开关）、
  `tests/test_kvattn_stream.py`（17 条）、`tests/test_graph_decode_int8.py`（4 条）、
  `src/diagnostics/bench_int8_decode.py`、`probe_kvattn_scalar.py`；
  承接 D42，不碰 D06/D07/D09
