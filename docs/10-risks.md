# 10 · 风险与未解决问题

> 诚实记录所有已知风险、失败模式和悬而未决的问题。**定期回顾本文件。**

---

## 一、技术风险

### 风险 1：表示漂移（严重性：高）

**问题：** 微调或升级模型后，旧的记忆文件可能失效——因为模型的"语言"变了。

**影响：** 对一个积累了长期记忆的单用户模型，这是灾难（记忆断了 = 身份断了）。

**缓解：**
- 记忆模块与语言模型架构**解耦**（第一版就要定下来）
- 记忆表示空间**冻结**，永不变
- 记忆文件带 `model_hash` 校验
- 提供"记忆迁移"工具（模型更新时转换旧记忆）

### 风险 2：训练记忆行为（严重性：高）

**问题：** 让模型学会"何时写、何时读、如何自然融入"是**最难的部分**。

**影响：** 做不好，记忆功能形同虚设——要么什么都记（淹没），要么该记的不记。

**缓解：**
- 大规模合成状态跟踪数据（见 08）
- 先用小规模验证行为是否可学
- 分阶段：先教"记住"，再教"自然融入"

### 风险 3：非标准架构无法用 GGUF / llama.cpp（严重性：高）

**问题：** 双通路 + 交叉注意力 + 记忆模块，标准推理框架不支持。

**影响：** 无法用现成的量化 / 部署工具链。

**缓解：**
- 短期：PyTorch + `torch.compile` 直接推理（4060 上估计 20-30 tok/s）
- 长期：写自定义 C++ 推理引擎（工作量大）
- 或者：向 llama.cpp 贡献支持

**这是本项目最现实的工程障碍。**

### 风险 4：自定义推理的批处理掩码 bug（严重性：中-高）

**问题：** 若未来支持多用户，块对角掩码写错会导致跨序列注意力泄漏。

**缓解：**
- 单元测试专门验证隔离性
- 当前设计为单用户，风险暂时不激活
- 若支持多用户，必须先做隔离测试

### 风险 5：双通路的计算开销（严重性：中）

**问题：** 双通路使单 token 计算量约为单模型的 1.2-1.5 倍。

**影响：** 速度下降。

**缓解：**
- 预测编码门控（闲聊时 Agent 关闭）
- 投机解码、MTP 等推理优化（见 05）
- 目标：净效果仍优于基线

### 风险 6：长上下文 KV Cache 管理（严重性：中）

**问题：** 200-500K 上下文在 8GB 显存上不可能全放。

**缓解：**
- 三层缓存（L1 GPU / L2 CPU RAM / L3 SSD）
- 记忆令牌替代庞大 KV
- 滑窗注意力

### 风险 7：训练显存压力（严重性：中）

**问题：** 7.9B 双通路的 QLoRA 训练，4060 8GB 很紧张。

**缓解：**
- 梯度检查点、梯度累积
- 分阶段训练（先训交叉注意力，再训 LoRA）
- 必要时用 Kaggle 免费 GPU（T4x2 / P100）

### 风险 15：量化执行路径效率不足（严重性：**高**，已实测发生）

**S2 实测（2026-09-21，见 [reports/s2-speed-diagnosis.md](../reports/s2-speed-diagnosis.md)）：**

- bitsandbytes 的 4-bit 矩阵乘在本机只有 **47 GB/s 有效带宽**（fp16 能打满 234 GB/s），**比 fp16 还慢 1.26 倍**。
- 结果：4-bit 解码 **10.6 tok/s**，仅为带宽理论上限（~116 tok/s）的 **9%**。
- bnb 自检通过但 `lib.get_compute_capabilities()` 报 CPU-only → CUDA 符号不可用，走回退路径。6 个 CUDA 版本 + 5 种加载配置**全部无效**。

**派生风险（更根本）：**

| 精度 | 带宽上限 | 能否达到 60+ tok/s 目标 |
|------|:---:|:---:|
| fp16 / bf16 | ~29 tok/s | ❌ **物理上不可能** |
| 8-bit | ~58 tok/s | ❌ 刚好差一点 |
| 4-bit | ~116 tok/s | ✅ 只有这条路 |

**影响：** 里程碑 2 的"60+ tok/s"目标**只能靠 4-bit 级有效位宽达成**。若量化路径始终修不好，目标需下调或改用非 PyTorch 推理栈。

**缓解：** 见 **D26** 的四条候选路径（GGUF+llama.cpp / 修 bnb / 换后端 / 先推进 S3）。**S3 的验收不测速度**，所以此风险不阻塞里程碑 1。

---

> **⚠️ 2026-09-22 更正（以 [D27](../docs/13-decisions.md) 为准）：上面 L87 / L89 两条实测结论是错的。**
>
> - **bnb 没有回退 CPU。** `cextension.lib._lib` 就是 `libbitsandbytes_cuda124.dll`，CUDA 符号齐全；profiler 里 `bitsandbytes::gemm_4bit` 有 **Self CUDA = 14.96 ms / 200 次**；bs=512 时 **21.0 TFLOPS**。`get_compute_capabilities` 报错只是因为**该符号不在 0.50.2 的导出表里**，而 bnb 对任何缺失符号都返回同一句误导性的 "CPU-only version" 文案。
> - **"47 GB/s" 是小形状下的启动延迟假象**，不是带宽。真实模型内 bnb 的有效带宽约 **135 GB/s**。
> - **真正的风险不是"量化执行路径效率不足"，而是"每 token 约 8000 次算子派发"。** 实测 `CPU enqueue-only 76.92 ms/step` ≈ `wall 77.02 ms/step`（**GPU 忙 ≈ 0.10 ms**）→ **100% CPU 发射受限**。占比：eager 逐元素/拷贝 **78.9%** / bnb gemm **17.1%** / attention **4.0%**。
>
> **修订后的风险表述：** 风险 15 应从"量化后端不好"改为 **"PyTorch eager 在 Windows 上的算子派发开销吃掉了全部速度预算"**。已实测排除的修法：torchao int4/int8、transformers 官方编译入口、`torch.compile` default / reduce-overhead。**剩余路径：① 自写精简前向（与 S3 合流）② 换运行时（WSL2+Linux）。** 严重性维持 **高**，但**性质从"后端缺陷"变为"运行时/实现工作量"** —— 这是可控的工程问题，不是死路。

## 二、数据风险

### 风险 8：上次训练乱码（已发生）

**问题：** 用户曾在云端训练，输出乱码。

**推测原因：** chat template 不匹配。

**规避：**
- 训练数据严格使用基座原生 chat template
- 训练后立刻做推理验证
- 保存训练模板，推理时严格一致

### 风险 9：数据合成成本与质量

**问题：** 状态跟踪数据现实中几乎没有，必须合成。

**影响：** 合成质量直接决定记忆功能成败；合成需要 API 成本。

**缓解：**
- 用户可提供 API 额度
- 先小批量试，验证格式有效再扩大

### 风险 10：数据量差距

**问题：** 闭源模型用 10-30 万亿 token，本项目只能用几千到几百万条。

**影响：** 知识广度差距无法弥补。

**缓解：** 接受这个限制，聚焦窄场景（RP / 对话）。

### 语言顺序相关风险（风险 14，编号 L1-L6）

训练顺序（先英文后中文，D18）本身带来一组风险，完整分析与缓解见 [15-language-plan.md](15-language-plan.md) 第七节：

| 编号 | 风险 | 缓解 |
|:---:|------|------|
| L1 | 中文能力退化（LoRA 覆盖基座原有中文） | 固定中文评测集持续监测 |
| L2 | 中英适配器互相干扰 | 语言判定后**只激活一个** |
| L3 | 中英混杂边界行为不可预测 | 中文数据强制含混杂样本 + 专项评测 |
| L4 | 英文阶段地基被中文样本污染 | 英文阶段严格语言过滤 |
| L5 | 顺序被打破（图快而中英同训） | 任何变更必须记录为新决策 |
| L6 | 30-50% 数据比例是估计值 | 做消融实验并记录结果 |

## 三、产品 / 伦理风险

### 风险 11：记忆的敏感性

**问题：** 单用户模型的记忆 = 用户的私人日记。

**缓解：**
- 记忆文件加密
- 备份策略（记忆丢失 = 身份断裂）
- 明确的删除 / 遗忘接口

### 风险 12：遗忘机制的设计难度

**问题：** 忘得太少会淹没，忘得太多会崩人设。这个平衡很难调。

**缓解：** 参考人脑的遗忘曲线，按重要性和时间双重加权。

### 风险 13：仿生人身份连续性的哲学问题

**问题：** 若模型承载了长期记忆，它是否具有某种"自我"？模型升级后是否还是"同一个"？

**状态：** 不是技术问题，但会影响设计决策（例如：是否允许记忆迁移）。
