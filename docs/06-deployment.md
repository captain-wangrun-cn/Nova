# 06 · 部署、缓存层级与单用户设计

---

## 一、DeepSeek 式缓存层级（"高缓存 + 持久"）

```
L1: GPU 显存     ~7 GB     活跃 KV Cache      纳秒级     <- 最快
L2: CPU 内存     ~32 GB    热 KV Cache        微秒级     <- 大容量
L3: SSD          ~1 TB     冷 KV + 记忆文件    毫秒级     <- 持久
---------------------------------------------------------
                    按需换入换出
```

| 层 | 内容 | 生命周期 |
|----|------|----------|
| L1 | 当前对话的 KV | 秒级 |
| L2 | 最近几个会话的 KV | 小时级 |
| L3 | 记忆令牌 + 归档 KV | **永久** |

### 关键设计

1. **前缀缓存**：系统提示词 / 角色卡永远不变 -> 常驻 L1，永不重算
2. **会话缓存**：会话中不断累积 -> L1，满了往 L2 挤
3. **记忆令牌**：会话结束压缩成记忆令牌 -> 写 L3（模型原生持久数据）
4. **归档 KV**：重要的完整对话 -> 存 L3，需要时精确恢复

**记忆令牌比 DeepSeek 的 KV 缓存更先进**：KV 无损但庞大，记忆令牌有损但极小。长期记忆用令牌，短期精确回忆用 KV。

## 二、KV Cache 与语义记忆：两种东西

| | KV Cache | 语义记忆 |
|--|----------|----------|
| 本质 | 计算缓存 | 认知记忆 |
| 内容 | 精确的注意力键值（无损） | 压缩的表征（有损） |
| 共享性 | **相同前缀可安全共享** | **绝对不能跨用户共享** |
| 出错后果 | 计算错误 | 隐私泄露 + 记忆串味 |

### 为什么 DeepSeek 的磁盘 KV Cache 是安全的

它的机制是**前缀哈希**：

```
请求 A: [系统提示词][用户A的问题]...
请求 B: [系统提示词][用户B的问题]...
              ^
        这一段完全相同
              v
    哈希相同 -> 复用这段 KV Cache  OK

用户A的问题 != 用户B的问题
              v
    哈希不同 -> 各存各的，不共享   OK
```

安全性来自：**只有内容完全相同时才共享。** 内容不同 -> 缓存键不同 -> 天然隔离。

相关技术：vLLM prefix caching、SGLang RadixAttention、LMCache。

## 三、多用户场景的风险（若未来要支持）

用户曾问："一个模型可能需要服务不同用户……我担心缓存会有一些问题？"

### 风险 1：跨用户记忆串味（最严重）

记忆令牌是**压缩的、有损的、语义化的**。若用户 A 的记忆被误加载到用户 B 的请求：

- 不是"计算错误"这种小问题
- 而是**用户 B 的模型突然"记得"用户 A 的私事**
- 且因为是压缩表征，**无法审计**里面到底有什么

**必须硬隔离：**

```
memory/
  user_<uid>/
    char_<cid>/
      session_<sid>.safetensors
```

每个请求进来，只加载该用户的记忆。永远不做跨用户匹配——哪怕内容"看起来相似"也不行。

### 风险 2：批处理时的注意力泄漏（真正的工程陷阱）

服务端会把多个用户的请求打包成一个 batch 一起前向传播：

```
batch = [用户A序列, 用户B序列, 用户C序列]

x 如果注意力掩码写错 -> 用户A能"看到"用户B的 token
OK 正确做法：块对角掩码（每个序列只能看到自己）
```

标准框架（vLLM/SGLang）用 PagedAttention 已处理。**但本架构是非标准的**（双通路 + 记忆模块），如果自己写推理代码，这块必须自己实现正确——这是最容易出 bug 的地方。

### 风险 3：记忆污染

一个用户的记忆文件损坏或异常，不能影响其他用户。需要：
- 加载失败时降级（跳过记忆，正常对话）
- 记忆文件加校验

## 四、一个重要的设计澄清

**如果两个用户和同一个"角色"聊天，角色应该记得另一个用户说过的话吗？不应该。**

| 内容 | 存在哪 | 是否共享 |
|------|--------|:---:|
| 角色的性格、说话风格 | **模型权重** | 所有用户共享（这是"人格"） |
| 与某个用户的具体经历 | **记忆文件** | 按用户隔离（这是"私人记忆"） |

类比：一个演员的演技（权重）对所有观众一样，但他和每个朋友的具体交情（记忆）是私人的。

## 五、单用户模型（仿生人方向）——本项目的选择

用户提出：

> "如果一个模型只允许一个人，一个相同的来源，一个相同人格调用呢？或许适用于仿生人领域，就像自己的大脑只能自己请求？"

### 为什么这不是荒诞，而是更合理

**多租户是云时代的产物，不是技术必然。** 多用户共享一个模型，唯一原因是算力贵、要摊薄成本。这是商业约束。

但个人设备（笔记本、手机、机器人）的**默认形态就是单用户**。

| 问题 | 多用户 | 单用户 |
|------|--------|--------|
| 记忆隔离 | 需要命名空间、鉴权、审计 | **不存在这个问题** |
| 隐私 | 靠策略保证（可能出错） | **靠架构保证（不可能泄漏）** |
| 记忆串味 | 需小心批处理掩码 | **物理上不可能** |
| 个性化 | 通用模型 + 提示词 | **可直接微调到这个人** |
| 复杂度 | 高 | 低 |

### 连续性 = 身份

一个只服务你的模型，运行一年、五年、十年，它积累的记忆**就是你的记忆**。这时它不再是一个工具，而是一个**连续的身份**。

对仿生人来说，这不是可选特性，这是**定义**：
- 仿生人的"我"，就是它积累的全部记忆
- 记忆断了，它就不是它了
- 记忆被污染，它的人格就崩了

**所以：单用户模型 + 持久记忆 = 人造的自我。**

### 但引出两个新的核心问题

1. **遗忘**（见 03-memory-system.md 第八节）：永远不忘的模型会被淹没、变迟钝、成为隐私噩梦
2. **表示漂移**（见 03 第七节）：升级模型时旧记忆会失效。解决：记忆模块与语言模型架构解耦，记忆表示空间冻结

### 架构上的两条硬约束

1. **记忆模块冻结**——语言模型可升级，记忆表示空间永不变
2. **记忆命名空间保留**，但只用一个（`self`）——保留扩展性，不为多用户设计，但也不写死

## 六、部署格式问题（待解决）

**最大的挑战不是训练，而是推理部署：**

- llama.cpp / GGUF **不支持**这种自定义架构
- 短期方案：PyTorch + `torch.compile` 直接推理（4060 上估计 20-30 tok/s）
- 长期方案：写自定义 C++ 推理引擎（工作量大）
- 或者：等社区支持 / 自己贡献 GGUF 支持

**这是本项目最现实的工程风险之一。**

**为什么会这样（原理说明见 [16-model-anatomy.md](16-model-anatomy.md)）：**

模型文件里**没有架构代码**，只有权重 + 配置（`config.json` 里的架构名只是一个"类名指针"）。真正实现架构的代码住在**运行它的引擎**里：transformers 是 `modeling_*.py`，llama.cpp 是一堆硬编码的 `build_*()` 函数。

**所以"部署这个模型"= 让某个引擎实现我们的计算图。** llama.cpp 只认它内置的架构名，双通路 / 交叉注意力 / 门控 / 工具头它都不认识 → 必须自己实现。

路线阶梯（详细对照表见 16 号文档第四节）：

| 路线 | 工作量 | 何时考虑 |
|:---:|:---:|------|
| PyTorch 自定义 `nn.Module` | 最小 | **第一版就用这个**（训练也必须是它） |
| + torch.compile / 量化 / 手写 KV Cache | 小-中 | 里程碑 2 提速 |
| ONNX / TensorRT | 中 | 分支结构简单后 |
| 自研 C++/CUDA 引擎 | 很大 | 长期，或性能确实不够时 |

## 七、记忆文件的安全性

对单用户模型，记忆就是"你的日记"，**敏感性极高**：

- 建议磁盘加密（至少对记忆文件）
- 记忆文件不应明文可读（虽然内容是张量，但仍是隐私）
- 备份策略需考虑（记忆丢了 = 身份断了）
